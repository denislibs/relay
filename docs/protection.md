# Защита от флуда, спама и простого DDoS

Один VPS (denigram.site), до ~1000 человек. Защита в три слоя:

1. **nginx** — грубое сито по IP: частота запросов, одновременные соединения, тайм-ауты против slowloris,
   размер тела. Срабатывает до Bun и базы.
2. **Сервер** (`apps/server/src/domain/flood.ts`) — лимиты на *пользователя*: сообщения, пересылка, чаты,
   контакты, поиск, реакции, «печатает…», звонки, выдача учёток TURN и токенов LiveKit. Ответ — `flood` с
   `retryAfter` (как `FLOOD_WAIT_X` в Telegram).
3. **WebSocket** (`apps/server/src/http.ts`, `WS_LIMITS`) — кадров на сокет в секунду и минуту, отказов flood
   подряд, сокетов на пользователя и на сеанс.

Плюс вход: лимиты на номер, адрес, страну (код номера) и суточный бюджет кодов на весь сервер.

## Что видит клиент

| Откуда | Ответ |
|---|---|
| HTTP, сервер | `429`, заголовок `Retry-After: N`, тело `{"code":"flood","retryAfter":N}` |
| HTTP, nginx | то же: `error_page 429` отдаёт JSON (`retryAfter` — 5 с, условно) |
| WebSocket | `{"op":"err","reqId":…,"code":"flood","retry":false,"retryAfter":N}` |
| WebSocket, злоупотребление | закрытие с кодом `4008` — клиент переподключается с самой долгой паузой |
| Сокетов слишком много | `/ws` отвечает `429` до upgrade |

Веб-клиент (`apps/web/src/flood.ts` — разбор и текст «через 12 с / 3 мин / 2 ч»):

- **Поле ввода / отправка.** Сообщение под лимитом — не «не отправлено»: остаётся с часиками, очередь
  отправки ждёт `retryAfter` и продолжает в том же порядке (`floodWait` в `packages/sync-engine/src/engine.ts`).
  В статусе движка — `floodUntil`; страница показывает тост «Слишком много сообщений подряд — остальные уйдут через N с».
  Медленный режим группы — по-прежнему отказ (сообщение «не отправлено» с причиной), как было.
- **Реакции** — откатываются в ленте, тост «Слишком много реакций. Попробуйте через N с».
- **Звонки** — 1:1: экран звонка «Слишком много звонков, подождите»; групповые: тосты для начала, входа и приглашений.
- **Вход** — под полем ошибки «Слишком много попыток. Попробуйте через 10 мин» (секунды из ответа); QR-код
  обновляется после срока, а не каждые 5 с.
- **Новая группа / канал / личный чат** — текст ошибки с временем.
- **Поиск** — при flood отвечает с устройства (локальные результаты), без ошибки.
- **Контакты и прочие операции очереди** (`ops.ts`) — 429 повторяется с нарастающей паузой.

## Лимиты сервера на пользователя

Таблица — `LIMITS` в `apps/server/src/domain/flood.ts`. Окна фиксированные, по часам (счётчик `hit()` в Valkey,
общий для всех процессов). Превышено любое окно — отказ до конца самого долгого из превышенных. Отказы тоже
считаются: долбёжка не пролезает, но и ожидание не продлевает. Valkey недоступен — лимиты не мешают работе.

| Имя | Окна (n / сек) | Где |
|---|---|---|
| `send` | 30/10, 120/60, 1500/3600 | кадр `send` (и отложенные) без пересылки |
| `forward` | 100/30, 1000/3600 | кадр `send` с `forward` (выделение до 100 разом) |
| `react` | 30/10, 600/3600 | кадр `react` |
| `typing` | 10/5 | кадр `typing` — сверх лимита молча отбрасывается |
| `chatCreate` | 5/60, 50/сутки | `POST /chats` (группа, канал) |
| `directOpen` | 30/60, 300/сутки | `POST /chats/direct` |
| `contactAdd` | 20/60, 300/сутки | `POST /contacts` |
| `lookup` | 30/60, 500/сутки | `POST /users/resolve` (номер, @имя — перебор номеров) |
| `search` | 30/10, 1000/3600 | `/search`, `/search/media|people|channels` (не `/search/top`) |
| `callRing` | 10/60, 60/3600 | звонок 1:1 (`callRequest`, ответ `{ok:false, reason:'flood'}`) |
| `callAccept` | 20/60, 200/3600 | ответ на звонок — выдача учётки TURN |
| `groupCallStart` | 5/60, 30/3600 | начать звонок группы или конференцию |
| `groupCallJoin` | 20/60, 300/3600 | вход в звонок группы, по ссылке — выдача токена LiveKit |
| `groupCallInvite` | 10/60, 100/3600 | позвать в конференцию (звонит людям) |

Прежние частные лимиты остаются как были: превью ссылок 30/мин, просмотры постов 1/с, сигналинг звонка 60/с,
ключи группового звонка 20/с, ссылки на звонок, загрузки (`uploadLimits.ts`), медленный режим, наблюдение за каналами.

### WebSocket

`WS_LIMITS` в `apps/server/src/http.ts`:

| Предел | Значение | Что будет |
|---|---|---|
| кадров в секунду на сокет | 100 (`WS_RATE`) | закрытие `4008` |
| кадров в минуту на сокет | 1800 | закрытие `4008` |
| отказов flood в минуту на сокет | 30 | закрытие `4008` (клиент не слушает `retryAfter`) |
| сокетов на пользователя | 30 | `429` на `/ws` |
| сокетов на сеанс (вкладки одного браузера) | 16 | `429` на `/ws` |

Сокеты считаются в процессе (на одном VPS процесс сервера один). Несколько процессов за балансировщиком —
предел на процесс, то есть общий — `N × значение`.

## Вход

| Предел | Значение | Где |
|---|---|---|
| кодов на строку логина (номер, @имя) и на аккаунт | 5 в час | `login.ts`, Postgres |
| кодов с адреса | 30 в час | `login.ts` |
| неверных кодов на цель | 15 в час | `login.ts` |
| кодов на страну (код номера: `+7`, `+44`, `+380`) | 500 в час (`loginPrefix`) | `flood.ts` |
| кодов на весь сервер | 5000 в сутки (`loginGlobal`) | `flood.ts`; 80% — `console.warn`, сверх — отказ всем до полуночи UTC |
| сообщений бота Telegram | 300 в сутки (`TELEGRAM_DAILY_CAP`) | `codeDelivery.ts` |
| «Войти через Telegram» с адреса | 20 в час (`telegramLogin.ts`) и 5 в минуту (`telegramIp`) | |
| «Войти через Telegram» на весь сервер | 2000 в час (`telegramGlobal`) | |

Отказы по номеру, адресу и аккаунту несут `retryAfter` — секунды до того, как старейшая попытка выйдет из часа.
Страна и бюджет считаются только для запросов, прошедших свои лимиты: перебор с одного адреса бюджет не съест.

**День запуска.** Почти все свои — `+7`: если регистраций больше 500 в час, поднять `RELAY_LIMIT_LOGIN_PREFIX`
(например `2000/3600`). Бюджет на сутки исчерпан атакой — отказ всем; в логе `flood: loginGlobal budget exhausted`.
Поднять `RELAY_LIMIT_LOGIN_GLOBAL` и перезапустить сервер.

## Настройка без сборки

Переменные окружения сервера (`docker-compose` → `server.environment`), перезапуск сервера:

```
RELAY_LIMIT_SEND=20/10,600/3600      # окна через запятую: число/секунды
RELAY_LIMIT_LOGIN_PREFIX=2000/3600
RELAY_LIMIT_TYPING=off               # выключить один лимит
RELAY_LIMITS=off                     # выключить все лимиты flood.ts (аварийно; WS и вход в Postgres — остаются)
```

Имя переменной — имя лимита в верхнем регистре со `_`: `groupCallJoin` → `RELAY_LIMIT_GROUP_CALL_JOIN`.
Не разобралось — действует таблица. `WS_LIMITS` и лимиты входа в Postgres — в коде.

Посмотреть счётчики: `valkey-cli --scan --pattern 'relay:rate:fl:*'` (ключ — `rate:fl:<имя>:<кто>:<окно>:<номер окна>`).

## nginx

Сниппеты — `docker/nginx/limits/`, кладутся в образ прокси (`/etc/nginx/snippets/limits/`), подключаются из
`docker/nginx/production.conf`. Правка — пересборка образа (`compose build proxy`); `dev.conf` их не использует.

| Файл | Где | Что |
|---|---|---|
| `http.conf` | http | зоны, коды 429, адреса Telegram |
| `server.conf` | оба server | тайм-ауты, соединения с адреса (200), JSON-ответ 429 |
| `api.conf` | `@api` | API 20 r/s (+200), вход 10 r/мин (+10), заявки загрузок 5 r/s (+60), webhook 30 r/s; тело ≤ 4 МБ |
| `ws.conf` | `/ws` | подключений 2/с (+20), открытых с адреса 60 |
| `livekit.conf` | `/livekit/` | подключений 2/с (+30), открытых с адреса 20 |
| `media.conf` | `:8333` | 50 r/s (+500) — экран чата тянет десятки превью |
| `cloudflare.conf` | http, **выключен** | настоящий адрес из `CF-Connecting-IP` |

Строгая зона входа — `/auth/code|signin|signup|password/check|password/recover…|telegram|qr|passkey/finish`.
Опросы (`/auth/qr/poll`, `/auth/telegram/poll`, раз в 2 с) и `/auth/config` — в общей зоне.

Webhook бота (`/auth/telegram/webhook`) принимается только с сетей Telegram `149.154.160.0/20` и `91.108.4.0/22`
(остальным — 404, как при неверном секрете; секрет в заголовке сервер проверяет всё равно). Если Telegram
сменит адреса — `geo $relay_from_telegram` в `http.conf`.

Тайм-ауты (против slowloris): заголовки 10 с, пауза в теле 20 с, пауза при отдаче 30 с, keep-alive 30 с,
оборванные — сбросом (`reset_timedout_connection`). Тело API — не больше 4 МБ (JSON; файлы идут в `:8333`).

За одним адресом бывает много людей (мобильный CGNAT, офис, общежитие): пределы по IP с запасом. Жалобы
«не пускает» при массовом входе из одной сети — поднять `burst` в `api.conf`/`ws.conf`. В логе nginx
отказы видны как `limiting requests` / `limiting connections` (уровень warn).

Проверка конфига: `docker compose exec proxy nginx -t`.

## Cloudflare перед сервером (позже)

Что даст: скрытый адрес VPS, поглощение объёмных атак (L3/L4 и HTTP), кэш статики, WAF и rate limiting на краю.

**Работает через Cloudflare без изменений:**

- сайт, API, `/ws` — WebSocket Cloudflare проксирует. Тайм-аут простоя у Cloudflare ~100 с, а клиент в тишине
  шлёт кадр только раз в 90 с (сверка `safetySyncMs`) — впритык: перед включением добавить пинг раз в ~30 с;
- `/livekit/` — сигналинг LiveKit тоже WebSocket.

**Не работает через Cloudflare:**

- **`:8333` (медиа из S3).** Обычный прокси Cloudflare пропускает только свои порты (HTTPS: 443, 2053, 2083,
  2087, 2096, 8443) — 8333 среди них нет. Предложение: вынести медиа на поддомен
  **`media.denigram.site:443`** — отдельный `server` в nginx с тем же содержимым, что сейчас у `:8333`
  (`server_name media.denigram.site; listen 443 ssl;`, сертификат на поддомен), и `S3_PUBLIC_ENDPOINT=https://media.denigram.site`.
  Подпись ссылок S3 включает хост — поменять endpoint и хост вместе, старые ссылки истекут сами (минуты).
  Медиа через Cloudflare: следить за условиями (большие видео и файлы — не «веб-контент»; при объёмах — R2 или
  поддомен без прокси, «серое облако»). Загрузки PUT — до 100 МБ на запрос на бесплатном плане: части
  multipart (`s3multipart.ts`) должны быть меньше.
- **UDP: TURN (coturn, 3478 и 49160–49200) и медиа LiveKit (7881/tcp, 50000–50060/udp)** — остаются напрямую
  на адрес VPS (DNS-запись без прокси, например `turn.denigram.site`). Адрес VPS при этом виден; защита — лимиты
  выдачи учёток (`callAccept`, `groupCallJoin`) и `user-quota`/`total-quota` в `docker/coturn`.

**Порядок включения:**

1. Медиа — на `media.denigram.site:443` (см. выше), проверить загрузку и просмотр.
2. DNS `denigram.site` и `media.` — через Cloudflare (оранжевое облако); `turn.` — серое.
   SSL/TLS — Full (strict), сертификат на сервере остаётся.
3. Раскомментировать `include /etc/nginx/snippets/limits/cloudflare.conf;` в `production.conf`, сверить
   сети с https://www.cloudflare.com/ips/, пересобрать proxy. Без этого все лимиты по IP станут общими на всех
   (адрес — Cloudflare), а webhook Telegram отсечётся.
4. Файрвол VPS: 80/443 — только из сетей Cloudflare (иначе их обходят по прямому адресу); UDP и TURN — для всех.
5. Сменить адрес VPS, если прежний уже светился (атака на прямой адрес Cloudflare не остановит).
6. Webhook Telegram — через Cloudflare работает (адрес Telegram придёт в `CF-Connecting-IP`).

`TRUST_PROXY=1` у сервера менять не нужно: nginx дописывает в `X-Forwarded-For` уже настоящий адрес клиента.
