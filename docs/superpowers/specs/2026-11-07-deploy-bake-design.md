# Наблюдение после выката с автооткатом (bake)

Дата: 2026-11-07. Статус: дизайн одобрен владельцем.

## Зачем

`deploy.sh` откатывает выкат, если сервисы не поднялись или не прошёл smoke (первые секунды). Поломки, которые
проявляются через минуты под живым трафиком — рост 5xx, падения процесса, ошибки кадров WebSocket, ошибки
клиентов новой сборки, — сейчас ловят только тревоги, и откатывает человек. Нужна фаза наблюдения сразу после
выката: новая сборка проверяется по метрикам и при ухудшении откатывается сама.

Настоящая канарейка (часть пользователей на новой сборке) отложена: при двух пользователях доля трафика не даёт
сигнала. Судья из этой работы потом пригодится и ей — сменится только источник сравнения.

## Где в процессе

`deploy.sh` → `release <sha>` (checkout, pull, migrate, up, healthy, проверки, smoke) → **bake** → записать
`current`/`previous`. Bake — часть `release`, поэтому его провал идёт тем же путём, что провал smoke: откат на
прежнюю сборку, строка `FAILED` в `deploy/state/history`, ненулевой код (шаг CI красный). При откате
(`rollback.sh`, `NO_ROLLBACK=1`) bake не выполняется — откат не должен ждать 10 минут и откатываться сам.

Параметры (окружение `deploy.sh`):

- `BAKE_MINUTES` — длительность, по умолчанию `10`; `0` — пропустить (срочный хотфикс). Ручной запуск:
  `BAKE_MINUTES=0 deploy/deploy.sh <sha>`; в `deploy.yml` — вход workflow_dispatch `bake_minutes`.
- `BAKE_INTERVAL` — шаг опроса, `30` секунд.

Если наблюдаемость выключена (`RELAY_OBSERVABILITY` ≠ `1`), метрик нет: bake проверяет только процессы и
`/ready` (сигналы 1–2 ниже) и пишет об этом в лог.

`deploy.yml`: `timeout-minutes` задания выката поднять с 20 до 35 (выкат ~5 мин + bake 10 + запас).

## Судья: `deploy/bake.ts`

Один файл TypeScript без зависимостей. Запуск — одноразовым контейнером из уже скачанного образа server (в нём
есть bun), в сети стека, файл смонтирован только на чтение:

```
compose run --rm --no-deps -T -v "$RELAY_DIR/deploy/bake.ts:/bake.ts:ro" --entrypoint bun server /bake.ts <args>
```

Аргументы: новая сборка `--build <sha>`, прежняя `--base <sha>`, время начала наблюдения `--since <unix>`.
Делает один замер и печатает одну строку JSON: `{"verdict":"ok"|"fail"|"wait","reasons":[…],"numbers":{…}}`.
Цикл, время и откат — в `deploy.sh` (оболочка), решение — в `bake.ts` (чистая функция `judge(sample, base)`,
отдельно от запросов к VictoriaMetrics).

Процессы (сигнал 1) судья не видит изнутри контейнера — их проверяет `deploy.sh` на хосте: `RestartCount` и
`State.StartedAt` контейнеров server и worker не изменились с начала bake, статус `healthy`.

### База

Те же запросы по прежней сборке (`build="<base>"`) за час до начала выката: VictoriaMetrics хранит ряды 30 дней,
поэтому база есть и после замены контейнеров. Нет прежней сборки или у неё нет данных — база нулевая (пороги ниже
всё равно требуют абсолютного минимума).

### Сигналы и пороги

| # | Сигнал | Провал |
|---|---|---|
| 1 | server или worker перезапустился, не healthy | сразу (хост, `deploy.sh`) |
| 2 | `/ready` → `ok:false` | 2 замера подряд |
| 3 | `up{job=~"server\|worker"}` = 0 | 2 замера подряд |
| 4 | доля 5xx `relay_http_requests_total{status=~"5.."}` новой сборки | > 2 % и > 3× базы, при ≥ 20 запросах |
| 5 | ошибки кадров `relay_ws_frames_total{result="internal"}` | > 3× базы + 5 |
| 6 | `relay_client_errors_total{client_build="<sha>"}` | > 3× базы + 5 |
| 7 | p95 `relay_http_request_duration_seconds` новой сборки | > 2× базы и > 1 с, при ≥ 50 запросах |

Счётчики — `increase(…[окно])`, где окно — от начала bake до замера; база — `increase` за час, приведённый к
длине окна. Сигналы 4–7 при малом трафике не набирают минимума и молчат — это ожидаемо.

Вердикт `ok` — когда истекло `BAKE_MINUTES` без провала. `wait` — VictoriaMetrics ещё не видит новую сборку
(первый опрос через 15 с): не провал, пока не прошла половина времени bake; потом — провал «нет метрик».
Недоступна сама VictoriaMetrics — сигналы 3–7 пропускаются с предупреждением в логе (bake не должен откатывать
из-за поломки мониторинга), 1–2 продолжают работать.

## При провале

1. Лог `deploy.sh`: `bake failed: <сигнал>: <числа>` — только названия сигналов и числа, вывод публичный.
2. Откат на прежнюю сборку — существующий путь `main` → `release "$prev"`.
3. Тревога владельцу: `amtool alert add RelayDeployRolledBack severity=critical` с `summary` «Выкат <sha>
   откачен: <сигнал>» через alertmanager (бот тревог); без наблюдаемости — пропускается.
4. Шаг CI красный.

## Проверка

- `tools/ci/bake.test.ts`: `judge()` на наборах замеров — каждый порог срабатывает и не срабатывает на границе,
  малый трафик молчит, `wait` → провал после половины времени, недоступная VictoriaMetrics не откатывает.
  Разбор ответа VictoriaMetrics — на записанных ответах API.
- `tools/ci/deploy.test.ts`: `BAKE_MINUTES=0` пропускает bake; при откате (`NO_ROLLBACK=1`) bake не вызывается.
- На проде: обычный выкат с `BAKE_MINUTES=2` — вердикт `ok`, в логе числа. Провал без порчи кода: судья с
  `--base` = текущая сборка и искусственно заниженными порогами (`BAKE_TEST_STRICT=1`, только для ручного запуска,
  `deploy.sh` его не передаёт) должен вернуть `fail` — это проверяет запросы к живой VictoriaMetrics; откат
  проверен существующими тестами и прошлыми выкатами.
