# Звонки 1:1 — голос и видео, сквозное шифрование — исследование и план

Цель: голосовые **и видео**звонки в личных чатах, защищённые так, чтобы **сервер Relay не мог ни подслушать,
ни незаметно встать посередине**. Входящий звонит на всех устройствах, принят на одном — на остальных гаснет;
звонок живёт поверх навигации, переживает смену сети; в ленте остаётся «Пропущенный звонок» /
«Исходящий видеозвонок · 3:12».

Источники — tweb (`~/Documents/tweb/src/lib/calls`, UI в `src/components/call`, `topbarCall.tsx`) и
telegram-tt (`~/Documents/telegram-dd/src/lib/vibecalls`). Оба GPL: берём поведение, числа и решения, код не
переносим. Звуки и картинки Telegram не используем — свои тона.

Групповые звонки — отдельный проект (нужен SFU), см. в конце.

## Как это устроено в Telegram (коротко)

**Состояния клиента:** запрос → ожидание (у звонящего «Звоним…», у адресата «Входящий») → обмен ключами →
соединение → разговор → завершение. Сервер ведёт свою копию: Waiting → Requested → Accepted → Active → Discarded.

1. Звонящий отправляет `requestCall` с **хэшем** своей половины DH (`g_a_hash`) — обязательство.
2. Каждое устройство адресата получает звонок и сразу отвечает `receivedCall` — у звонящего «Ожидание» → «Звонок».
3. Адресат нажимает «Принять» → `acceptCall(g_b)`. Сервер отдаёт звонок первому принявшему, остальным
   устройствам — «звонок закрыт».
4. Звонящий получает `g_b`, раскрывает `g_a` (`confirmCall`). Адресат сверяет `sha256(g_a)` с обязательством.
   Из ключа — **4 эмодзи**: одинаковые у обоих — посредника нет.
5. Дальше WebRTC. Сервер пересылает только **зашифрованные ключом звонка** блобы (gzip + AES, счётчик против
   повторов): компактный JSON с ufrag/pwd/**DTLS-отпечатками**, кодеками, кандидатами (trickle ICE),
   состоянием микрофона/камеры. Раз отпечатки DTLS едут внутри зашифрованного, медиаканал привязан к ключу DH.
6. STUN/TURN — список с сервера вместе со звонком; если p2p запрещён настройкой — только TURN
   (`iceTransportPolicy: relay`), собеседник не узнаёт IP.

**Числа:** без ответа — 45 с; обмен ключами и переподключение — до 45 с; ни разу не соединившийся
транспорт — 20 с. Перезапуск ICE: `failed`, `disconnected` дольше 2 с, событие `online`, смена типа сети;
не чаще раза в 5 с; адресат ждёт 2 с, чтобы первым перезапустил звонящий.

**Медиа:** echoCancellation + autoGainControl всегда, шумодав — переключателем; камера ≤1920, ≤30 fps;
H.264 перед VP8. Камеру и экран заводят заранее «пустыми» дорожками, включение — `replaceTrack`. Микрофон —
`track.enabled = false`, собеседник узнаёт по DataChannel («у X выключен микрофон», «низкий заряд»).
Уровень голоса: свой — AnalyserNode, чужой — RTP audio-level. Качество — из `getStats`. Автозапуск звука
заблокирован — повтор на первый клик.

**Устройства и вкладки:** звонят все сессии; telegram-tt ведёт звонок в одной «главной» вкладке; при идущем
разговоре новый входящий — «занято». Закрыли вкладку — исходящий/идущий звонок завершается, входящий нет.

## Безопасность — модель угроз и ответы

Сообщения в Relay шифруются **на сервере** (не E2E). Для звонков планка выше: сервер — недоверенный
посредник. Он нужен, чтобы найти собеседника и передать пакеты, но не должен иметь возможности:

| Угроза | Ответ |
|---|---|
| Сервер / TURN слушает разговор | медиа — DTLS-SRTP точка-точка; через TURN идёт уже зашифрованное, ключей у TURN нет |
| Сервер подменяет SDP и встаёт посередине (две «половины» звонка) | сигналинг зашифрован ключом звонка из ECDH; отпечатки DTLS — только внутри шифра; **4 эмодзи** у обоих |
| Посредник подбирает свои ключи под те же эмодзи | обязательство: звонящий сначала шлёт хэш своего ключа, раскрывает только после ответа — один шанс из ~8·10⁹ |
| Сервер читает SDP: IP-адреса, кодеки, устройства | сигналинг зашифрован (AES-GCM), сервер видит только размер |
| Повтор / перестановка сигнальных пакетов | счётчик в каждом пакете, `callId` и направление в AAD, окно повторов |
| Собеседник узнаёт мой IP | настройка «Пиринговые соединения»: все / контакты / никто; по умолчанию напрямую только с контактами, с остальными — через TURN |
| TURN как прокси во внутреннюю сеть (SSRF) | coturn: `denied-peer-ip` для всех частных и служебных диапазонов, `no-multicast-peers`, `no-cli`, без TCP-релея к внутренним адресам |
| Чужие пользуются нашим TURN | временные учётки на звонок (HMAC, 2 ч), только участникам, лимит полосы и квота на пользователя |
| Звонки-спам и навязчивые звонки | приватность «Кто может мне звонить», блокировка, лимит частоты запросов, только личные чаты |
| Чужая вкладка / украденная cookie отвечает на звонок | кадры только после `prove` (ключ устройства), `callSignal` только в принявшую вкладку |
| Утечка ключа после звонка | ключи эфемерные на каждый звонок, неэкспортируемые (`extractable: false`), удаляются по завершении — прямая секретность |
| Камера/микрофон включены дольше нужного | захват — только по действию пользователя; все дорожки `stop()` при завершении, переходе в фон без звонка, ошибке |
| Подмена данных от собеседника ломает клиент | строгая проверка расшифрованного сигналинга (тип, размеры, допустимые строки SDP) до `setRemoteDescription` |
| Push раскрывает звонок | содержимое push шифруется (aes128gcm), TTL 45 с, уведомление снимается по `callEnded` |

**Честная граница:** веб-клиент загружается с нашего же сервера — взломанный сервер может отдать изменённый
JavaScript. Это предел любого веб-мессенджера; снижаем риск SRI, CSP без `unsafe-*` и (позже) подписанной
сборкой / PWA-кэшем. Метаданные (кто, кому, когда, сколько) сервер знает неизбежно — в истории они лежат
зашифрованными на диске, как сообщения.

### Протокол ключей (свой, по мотивам Telegram — проще, на WebCrypto)

ECDH X25519 (запасной вариант — P-256, если браузер не умеет), HKDF-SHA-256, AES-256-GCM. Всё через
`crypto.subtle`, ключи неэкспортируемые.

1. **Звонящий:** эфемерная пара `A`; в `callRequest` — `commit = SHA-256(pubA ‖ callId)`.
2. **Адресат** (принял): эфемерная пара `B`; в `callAccept` — `pubB`.
3. **Звонящий:** в `callConfirm` — `pubA`. Адресат проверяет `commit`; не совпало — завершить «ошибка
   безопасности».
4. **Оба:** `secret = ECDH(A, B)`; `transcript = SHA-256(callId ‖ caller ‖ callee ‖ commit ‖ pubA ‖ pubB)`;
   `HKDF(secret, salt = transcript)` → ключ сигналинга «звонящий→адресат», ключ «адресат→звонящий»,
   ключ эмодзи.
5. **Сигналинг** (`callSignal.data`): `{ seq, iv, ct }`, AES-GCM, AAD = `callId ‖ направление ‖ seq`.
   Внутри — offer/answer, ICE-кандидаты, состояние медиа. Принимаем только `seq` больше последних / в окне.
6. **Привязка медиа:** первый пакет каждой стороны — её DTLS-отпечаток (из `RTCCertificate`, сгенерированного
   на звонок). После соединения сверяем отпечаток **фактического** соединения (`getStats` →
   `certificate` удалённой стороны) с полученным по шифру. Не совпал — разрыв «ошибка безопасности».
7. **Эмодзи:** 4 индекса из ключа эмодзи (по 8 байт, mod размер таблицы ~300 обычных системных эмодзи).
   Показываем в шапке разговора; по нажатию — «Если у собеседника такие же эмодзи, звонок защищён».

Отдельный слой шифрования медиа (Insertable Streams / SFrame) для 1:1 ничего не добавляет: DTLS-ключи уже
сквозные и проверены. Понадобится для групповых звонков через SFU.

## Решения

### 1. Сервер — арбитр состояния, не участник разговора

Состояние звонка — на сервере в Valkey (общий для процессов, TTL): кто первым принял, кто занят, когда
истекло — решает сервер атомарно (Lua / `SET NX`). Содержимого сигналинга он не видит.

```
call:<id>    hash  { caller, callee, chatId, video, state, createdAt, acceptedAt, answeredBy }   TTL 2 ч
busy:<user>  str   <callId>
```

- **Занят:** `busy:<user>` — `SET NX` у звонящего при запросе и у адресата при принятии; занят — сразу
  `callEnded {reason:'busy'}`.
- **Таймауты** — задача очереди `dedupeKey: call:<id>:ring`, 45 с без принятия → `missed`. Соединение и
  переподключение видят клиенты (ICE) и сами шлют `hangup {reason:'disconnect'}`; сервер страхует общим
  TTL.
- **Длительность** считает сервер: от `accepted` до первого `hangup`.
- **История:** служебное сообщение `call` в личный чат `{ video, reason, duration }`, reason ∈
  `missed | declined | cancelled | busy | ended | failed`; одно на звонок.

### 2. Кадры протокола

Клиент → сервер (`packages/protocol`, `parseClientFrame`, `ws.ts`):

| op | поля | что делает сервер |
|---|---|---|
| `callRequest` | reqId, callId, chatId, video, commit | личный чат, не блок, приватность `calls`, не занят, лимит → `call:<id>`, `callIncoming` всем сокетам адресата, push офлайн-сессиям, задача 45 с |
| `callReceived` | callId | первый раз → `callRinging` звонящему |
| `callAccept` | callId, tab, pubB | атомарно «первый принявший»; `callAccepted {by, pubB, iceServers}` обоим; остальные вкладки и устройства адресата гаснут по `by` |
| `callConfirm` | callId, pubA | только от звонящего, только после accept → адресату |
| `callDecline` | callId | `declined` / `cancelled` |
| `callHangup` | callId, reason | конец, служебное сообщение, снять `busy:*` |
| `callSignal` | callId, data | непрозрачный шифротекст; только второму участнику, только принявшей вкладке; ≤ 64 КБ, лимит частоты |

Сервер → клиент: `callIncoming {callId, chatId, from, video, commit}`, `callRinging`, `callAccepted`,
`callConfirm`, `callSignal`, `callEnded {callId, reason, duration?}`. Все эфемерные — через шину, как
`typing`; долговечно только служебное сообщение. Сервер проверяет форму полей (длины ключей и commit), но
не содержимое шифротекста.

`iceServers` — временные учётки TURN; при «напрямую — никто» клиент ставит `iceTransportPolicy: 'relay'`.
Адресат решает сам по своей настройке и шлёт выбор в зашифрованном первом пакете — если хоть одна сторона
против p2p, обе идут через TURN.

`tab` — случайный id вкладки: сессия у вкладок одного браузера общая, а звонок должен быть в одной.

### 3. WebRTC: стандартный SDP, perfect negotiation, видео с первого этапа

- Внутри шифра — обычный SDP (`{ description }`), кандидаты (`{ candidate }`), состояние (`{ media }`).
  Конфликты встречных offer — perfect negotiation (вежливая сторона — адресат).
- **Видео сразу:** аудио- и видео-трансиверы `sendrecv` с первого offer; голосовой звонок — видеодорожка
  `null`. Включить камеру посреди разговора — `replaceTrack` без пересогласования; собеседник видит кадр
  по `media.cam = true`. Демонстрация экрана — третий трансивер, так же.
- Камера: ideal 1280×720, ≤ 30 fps, `maxBitrate` по слою; экран ≤ 1920, ≤ 30 fps, ~1,8 Мбит/с.
  Переворот и смена камеры/микрофона/динамика — `replaceTrack` / `setSinkId`; сохранённый deviceId
  пропал — берём по умолчанию.
- Предпочтение кодеков — `setCodecPreferences` (H.264, затем VP8), без правки SDP руками.
- Состояние медиа — DataChannel `state`, тоже зашифрованный (поверх DTLS он и так защищён; шифр нужен
  до открытия канала, пока идёт через сервер).
- Перезапуск ICE — правила Telegram выше; инициирует звонящий.
- Качество — `getStats` (RTT, потери, битрейт) → 0–4 полоски, при плохом — понижаем разрешение видео.

### 4. Клиент

**Где живёт:** `apps/web/src/calls/` — `callController.ts` (состояние, `RTCPeerConnection`, таймеры),
`callCrypto.ts` (ключи, HKDF, AES-GCM, эмодзи — с юнит-тестами), `media.ts` (getUserMedia, устройства,
уровень звука), `sounds.ts` (свои тона на WebAudio — без файлов).

**Канал «движок → страница»:** в `host-core.ts` новый `{ t: 'event', name, data }`; движок отдаёт кадры
`call*` как есть. Страница → движок — `engine.call({ type: 'callSignal', … })`. Ключи звонка в движок
не попадают — шифруем/расшифровываем на странице.

**Вкладки:** входящий виден во всех видимых вкладках, звонок — в одной (Web Lock `relay-call-ring`).
Принявшая вкладка держит lock `relay-call` весь разговор; остальные гаснут по `callAccepted.by.tab`.
Новый звонок при занятом lock — «Вы уже разговариваете в другой вкладке». Вкладку с разговором закрыли —
`hangup` в `pagehide`.

**UI** (по `docs/SMOOTH-UI.md`):
- кнопки «Позвонить» / «Видеозвонок» в шапке личного чата и в профиле (`Info.tsx`);
- `IncomingCall` — карточка поверх всего: аватар, имя, «Входящий видеозвонок», Принять / Принять без
  видео / Отклонить; предпросмотр своей камеры для видеозвонка — только после нажатия;
- `CallScreen` — статус («Звоним…», «Обмен ключами…», «Соединение…», таймер), **эмодзи** с подсказкой,
  значок «Сквозное шифрование», качество, видео собеседника во весь экран и своё в углу (перетаскивается),
  кнопки микрофон / камера / сменить камеру / экран / динамик / завершить; «у X выключен микрофон»;
- `CallBar` — полоска над шапкой, как `PlayerBar` (длительность, микрофон, завершить, развернуть);
  при видео — маленькое окно поверх чатов (и Picture-in-Picture по кнопке);
- служебный пузырь звонка в ленте с «Перезвонить»;
- позже — вкладка «Звонки» (готовый `CallRow`).
- новые иконки в `tools/icons/build_vk.py`: положить трубку, микрофон выкл., камера выкл., демонстрация
  экрана, сменить камеру, замок.

**Разрешения:** нет микрофона — звонок не начинаем, подсказка; нет камеры — продолжаем голосом.

### 5. Push и закрытые вкладки

Полезная нагрузка `{ type: 'call', callId, chatId, from, video }`, `ttl: 45`, `urgency: high`; только
сессиям без живого сокета. `sw.ts`: `requireInteraction: true`, кнопки «Принять» / «Отклонить»;
«Отклонить» — `fetch POST /calls/<id>/decline` из SW; «Принять»/клик — окно с `#call=<id>`, звонок
передаётся странице. По `callEnded` — закрыть уведомление (`tag: 'call-<id>'`).

### 6. Приватность

Два новых ключа в `PrivacyKey`, страницы в настройках приватности (как у Telegram):
- `calls` — «Кто может мне звонить»: все / контакты / никто + исключения. Заблокированный и запрещённый
  получают одинаковое «недоступен», без причины.
- `p2p` — «Пиринговые соединения»: все / **контакты (по умолчанию)** / никто.

### 7. Настройки → «Звонки» (динамики, микрофон, камера)

Новая страница `apps/web/src/ui/settings/Calls.tsx` (регистрируется в `settings/pages.ts`, пункт в
`Main.tsx` и в поиске по настройкам). Выбор хранится в настройках устройства (`apps/web/src/prefs.ts`,
`relay.prefs`, новая версия схемы) — это свойство конкретного компьютера, на сервер не уходит.

| Блок | Что внутри |
|---|---|
| Микрофон | список устройств (`enumerateDevices`), **живой индикатор громкости** (AnalyserNode), «Шумоподавление» ⇄, «Автоусиление» ⇄ |
| Динамики | список выходов (`setSinkId`, где браузер умеет; иначе пункт скрыт), кнопка «Проверить звук» — наш тестовый тон в выбранный выход, громкость звонка |
| Камера | список камер, **живой предпросмотр** (зеркально), «Качество видео»: авто / экономия трафика / высокое |
| Звонок | «Принимать звонки на этом устройстве» ⇄ (выкл — устройство не звонит, но видит пропущенные), мелодия входящего из своих тонов с прослушиванием |
| Приватность | ссылки на «Кто может мне звонить» и «Пиринговые соединения» (страницы на `PrivacyRule`) |

Правила:
- **Камера и микрофон включаются только кнопкой** «Проверить микрофон» / «Показать камеру», не при
  открытии страницы; уход со страницы, сворачивание вкладки или 60 с без действий — `stop()` всех дорожек.
- Нет разрешения — вместо списка подсказка, как разрешить в браузере; названия устройств без разрешения
  браузер не отдаёт — показываем «Микрофон 1», «Камера 1».
- Подключили/отключили устройство (`devicechange`) — список обновляется; выбранное пропало — берём
  системное по умолчанию и показываем это.
- Те же списки — в меню «⋯» прямо во время звонка (смена на лету через `replaceTrack` / `setSinkId`),
  выбор сохраняется сюда же.
- По `docs/SMOOTH-UI.md`: предпросмотр камеры появляется плавно после первого кадра, без чёрного мигания.

### 8. TURN

- `coturn` в `docker-compose` (профиль `calls`), UDP 3478 + диапазон релея, TLS 5349 (сети без UDP).
  В `docker-compose.secure.yml` публикуются только эти порты.
- Временные учётки (`use-auth-secret`): `username = <expiry>:<userId>`,
  `credential = HMAC-SHA1(secret, username)`, 2 ч, только участникам звонка.
- Жёсткая конфигурация: `denied-peer-ip` (10/8, 172.16/12, 192.168/16, 127/8, 169.254/16, 100.64/10,
  ::1, fc00::/7, fe80::/10 и адреса самих контейнеров), `no-multicast-peers`, `no-cli`, `fingerprint`,
  `user-quota`, `total-quota`, `max-bps`, логи без содержимого.
- Нужен уже на первом этапе: без него не работает «напрямую — только с контактами».

## Этапы

1. **Голос и видео 1:1, защищённые** — кадры и арбитр на сервере (Valkey + задача 45 с), протокол ключей
   и шифрованный сигналинг, проверка DTLS-отпечатка, эмодзи, coturn с временными учётками, приватность
   `calls` и `p2p`, канал событий движка, `callController`, `IncomingCall` / `CallScreen` с видео,
   кнопки в шапке, служебное сообщение, свои тона, перезапуск ICE, страница настроек «Звонки»
   (микрофон с индикатором, динамики с проверкой, камера с предпросмотром, приём на этом устройстве).
2. **Удобство** — демонстрация экрана, `CallBar` и мини-окно видео, push с кнопками, несколько вкладок,
   смена устройств, качество по `getStats`, шумодав, оценка звонка, вкладка «Звонки».
3. **Групповые звонки** — отдельный проект: SFU (LiveKit — Apache-2.0, mediasoup — ISC) плюс сквозное
   шифрование кадров (SFrame / Insertable Streams), иначе SFU видит медиа.

## Проверка

- Сервер (`docker compose --profile test run --rm test`): `calls.test.ts` + сценарий в
  `multiprocess.test.ts` — звонок, принятие на одном устройстве → второе гаснет, занят, 45 с → пропущен,
  блок и приватность, `callSignal` не уходит третьим лицам и в непринявшую вкладку, лимиты.
- `callCrypto.test.ts`: одинаковые ключи и эмодзи у сторон; неверный commit, подмена `pubA`/`pubB`,
  подмена шифротекста, повтор `seq` — отказ.
- **Тест «сервер посередине»:** прокси в тесте подменяет `pubB` своим ключом → у сторон разные эмодзи;
  подменяет DTLS-отпечаток → разрыв «ошибка безопасности».
- Браузер: Playwright, Chromium с `--use-fake-ui-for-media-stream --use-fake-device-for-media-stream`,
  два контекста на `https://127.0.0.1`: голосовой и видеозвонок → байты идут в обе стороны (`getStats`),
  эмодзи совпадают, включение камеры посреди разговора, «через TURN» (`relay`-кандидаты при `p2p = никто`),
  обрыв сети (остановить proxy) → «Переподключение…» → разговор продолжается, завершение → дорожки
  остановлены, в лентах служебное сообщение.
- Страница «Звонки»: с фейковыми устройствами Chromium — список не пустой, индикатор громкости
  двигается, предпросмотр показывает кадр; уход со страницы → `getTracks()` всех потоков в `ended`;
  выбранный микрофон и камера реально используются в следующем звонке (`getSettings().deviceId`).
- Встроенная панель браузера Claude для проверки не годится (воркеры и SW там не работают).
