# Защита переписки и файлов (без сквозного шифрования)

Ветка `feat/at-rest-encryption`. Цель: утечка любого одного компонента — дамп базы, бэкап, бакет S3, внутренняя
сеть, индекс поиска — не раскрывает переписку и файлы; удалённое перестаёт существовать; сеанс нельзя унести
вместе с профилем браузера.

Честно не обещаем: работающий сервер с доступом к KMS читает переписку (это не E2E); метаданные (кто, кому, когда,
размеры) видны; веб-клиент доверяет нашему серверу.

Принципы: никакой своей криптографии (WebCrypto: AES-256-GCM, HKDF, ECDSA P-256); шифр самоописываемый (версия
формата и ключа); каждый этап с переходным режимом (старое читается, новое пишется по-новому, задача догоняет);
dev без внешних сервисов (поддельный KMS).

## Решения этапа 0

- KMS: интерфейс + `FakeKms` (dev, тесты) + `VaultKms` (HashiCorp Vault / OpenBao, движок Transit). В compose —
  OpenBao в dev-режиме, чтобы настоящий путь тоже проверялся.
- Поиск: изолировать индекс сейчас, поиск на клиенте — как направление.
- Сроки: бэкапы данных — 30 дней, ключей — 7 дней.
- Аватарки, обои, музыка профиля не шифруются (публичные по смыслу).

## Итоговая архитектура (все этапы сделаны)

**Где что лежит и чем закрыто**

| Данные | Хранение | Чем открывается |
|---|---|---|
| Текст, разметка, превью ссылки, чек-лист, статья, вложение-метаданные | `messages.content` (bytea): `[формат][версия ключа][nonce][шифр+тег]`, AAD = `messages\|чат\|client_id\|content` | ключ чата (DEK) из `keys.chat_keys`, завёрнутый главным ключом KMS |
| Черновики | `drafts.content`, та же схема | ключ чата |
| Журнал `updates`, задачи `jobs` | только ссылки `{chatId, id}`; тела подтягиваются при `sync` | — |
| Файлы в S3 | формат RLF1: заголовок 24 байта + куски по 512 КБ AES-GCM, nonce = база‖номер, AAD = «relay-file\|номер\|последний» | ключ файла: в шифре сообщения (клиенту) и в `keys.attachment_keys` (воркеру); копии (превью, 720p) — ключи через HKDF |
| Индекс поиска | Meilisearch во внутренней сети, у сервера ключ только на поиск, бэкапа нет | — |
| Ключи | схема `keys`; бэкап отдельно, 7 дней (данные — 30) | главный ключ — только в KMS (Vault/OpenBao Transit) |

**Процессы**

- `keys` (`keyService.ts`) — единственный с учётными данными KMS; server и worker заворачивают/разворачивают через
  него по своим токенам (`KMS_PROVIDER=service`); журнал аудита, предел развёртываний в минуту с тревогой.
- Удаление «для обоих» и удаление чата — crypto-shredding: ключи старых версий удаляются, `NOTIFY` чистит кэши всех
  процессов; старый шифр в бэкапах данных больше не открыть, как только истёк бэкап ключей.
- TLS между сервисами (`tls.ts`): Postgres `verify-full` (+mTLS), Valkey `rediss`, https к S3/KMS/поиску;
  в production без TLS процесс не стартует.

**Сеанс, привязанный к устройству (этап 8)**

- Клиент (`packages/sync-engine/src/device.ts`) создаёт неизвлекаемый ключ ECDSA P-256 в IndexedDB `relay-device`.
  Первое `POST /session/refresh` (подпись «relay-device|refresh|nonce» по вызову `GET /session/challenge`, HMAC и
  2 минуты) привязывает публичный ключ к сеансу (`sessions.device_key`).
- После привязки долгий cookie `relay_session` сам по себе ничего не открывает: API требует короткий `relay_access`
  (10 минут, `session_access`), иначе `401 {code:'access_expired'}` + `x-relay-auth: refresh`. Обновить его можно
  только подписью ключом устройства — украденный cookie без ключа бесполезен через ≤10 минут.
- Клиент обновляет доступ заранее (страница — раз в 4 минуты и при возврате на вкладку) и по требованию: движок,
  страница и Service Worker оборачивают fetch — 401 «обнови» → подпись → повтор, без экрана входа и без стирания данных.
- WebSocket привязанного сеанса присылает `{op:'challenge'}`; кадры клиента ждут в очереди, пока не придёт
  `{op:'prove', sig}` (подпись «relay-device|ws|nonce»); неверная подпись или 10 секунд без неё — закрытие 4401.
- Выход забывает ключ устройства; следующий вход привяжет новый.

**Чего это не даёт** (без изменений): работающий сервер с доступом к KMS читает переписку; метаданные видны;
веб-клиент доверяет коду, который ему отдал сервер.
