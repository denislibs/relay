# Вложения в S3 с подписанными ссылками

Было: `POST /upload` с телом файла через Bun → том `files:/data/files`; `GET /files/:id` отдавал файл сам.
Стало: тело идёт мимо сервера, в данных (сообщения, IndexedDB, Cache Storage) остаётся только id вложения.

## Почему SeaweedFS, а не MinIO

Проверено 2026-10-18. MinIO community больше не выпускает сборки: с октября 2025 только исходники, с декабря 2025 —
режим поддержки, в 2026 репозиторий в архиве, а образы `minio/minio` и `minio/mc` в сентябре 2026 удалены с Docker
Hub (осталась копия на Quay без гарантий). Брать образ без обновлений безопасности для нового хранилища не стали.

Из двух альтернатив с S3 API выбран **SeaweedFS** (`chrislusf/seaweedfs:4.48`, Apache-2.0, сборка 2026-09-28):
- один процесс `weed server -s3` (master + volume + filer + S3), бакет создаётся `weed shell` из того же образа;
- учётки и права на бакет — JSON-файл (`docker/seaweedfs/s3.json`), без отдельного шага настройки;
- CORS для браузера работает по умолчанию (origin отражается, PUT/GET разрешены);
- подписанные ссылки SigV4 из `Bun.S3Client.presign` принимаются, `response-content-type` и
  `response-content-disposition` в GET соблюдаются, истёкшая ссылка — 403.

Garage (AGPL) тоже подошёл бы, но требует раскладки кластера и выпуска ключей через админ-API при каждом новом томе,
а CORS настраивается только через S3 `PutBucketCors`, который Bun не умеет — понадобился бы отдельный клиент.

## Поток

1. `POST /uploads {name, mime, size, w?, h?, kind?, duration?, waveform?}` → строка `attachments` со `status = 'pending'`
   и подписанный PUT на 5 минут (ключ = id). Размер ≤ 50 МБ проверяется здесь.
2. Клиент кладёт файл PUT-ом с выданным `mime` (XHR с прогрессом в воркере; 0–98 %, остаток — подтверждение).
3. `POST /uploads/:id/confirm` — только владелец (чужой получает 404). HEAD объекта: размер и тип должны совпасть с
   обещанными, иначе объект удаляется и ответ `upload_mismatch`; объекта нет — `upload_missing` (клиент начнёт заново).
4. `send` с вложением принимает только `ready` (`upload_pending` иначе).
5. `GET /files/:id` — владелец или участник чата, где вложение отправлено → 302 на подписанный GET на 10 минут,
   редирект кэшируется вдвое меньше. Тип и `Content-Disposition` задаёт подпись: активные типы (HTML, SVG, PDF…)
   всегда `application/octet-stream` вложением.

Брошенные `pending` старше суток удаляет раз в час вместе с объектом периодическая задача `uploads.sweep` в процессе-воркере (`sweepPendingUploads`).

## Клиент

- Движок (`upload`/`put` в `engine.ts`): ссылки не хранит; сеть пропала — ждёт переподключения, как раньше; 5xx,
  403 от хранилища (истёкшая ссылка) и `upload_missing` при живой сети — повтор через 1, 2, 5, 10, 30 с с новой
  ссылкой; `upload_mismatch`, `too_long` — сообщение failed.
- Service Worker: `<img>` идёт в no-cors, и ответ после редиректа на другой origin непрозрачный — его нельзя
  сохранить. Поэтому SW сам запрашивает `/files/:id` в режиме cors (`fetchMedia`); ключ кэша — `/files/:id`.

## Окружение

`S3_ENDPOINT` (сервер → хранилище), `S3_PUBLIC_ENDPOINT` (хост в подписанных ссылках для браузера), `S3_BUCKET`,
`S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `S3_REGION`. Ключи в `docker/seaweedfs/s3.json` — только для разработки.

## Известные ограничения

- Bun подписывает в PUT только `host`: длину и тип нельзя закрепить в подписи, поэтому их проверяет confirm. До
  истечения PUT (5 минут) владелец может перезаписать уже подтверждённый объект — только свой и только своими байтами;
  тип при выдаче всё равно задаёт подпись GET.
- В dev хранилище на `localhost:8333`, а cookie не различают порты: браузер шлёт `relay_session` и туда.
  Хранилище его игнорирует; в проде у хранилища должен быть отдельный домен.
- `Content-Disposition` не входит в `Access-Control-Expose-Headers` у SeaweedFS: `fetch()` его не видит, но обычное
  скачивание по ссылке браузер называет правильно.

## Перенос

`docker compose --profile tools run --rm migrate-files` (`apps/server/src/migrateFiles.ts`): копирует `ready`-вложения
с тома в бакет, повторный запуск пропускает уже перенесённые, сообщает отсутствующие файлы. Том после проверки можно удалить.
