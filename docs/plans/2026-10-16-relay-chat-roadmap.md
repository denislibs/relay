# Relay Chat — дорожная карта реализации

Офлайн-first мессенджер: Bun + Postgres на сервере, Preact + UI-кит Relay на клиенте, данные в SharedWorker, интерфейс получает живые подписки с патчами. Всё запускается в Docker.

Каждый этап — отдельный план в `docs/superpowers/plans/`, который даёт работающий и проверяемый результат сам по себе. Подробный план пишется перед началом этапа, чтобы опираться на интерфейсы, уже созданные предыдущими этапами.

## Сквозные решения (действуют во всех этапах)

- Монорепозиторий на Bun workspaces: `apps/server`, `apps/web`, `packages/protocol`, `packages/sync-engine`, `packages/relay-ui`.
- Всё запускается и тестируется в Docker Compose: `postgres:17-alpine`, образ сервера на `oven/bun:1.4.2`, отдельный сервис миграций; с этапа 5 — `minio` для медиа.
- Сервер — источник правды. Журнал изменений `updates(user_id, seq)` без дыр; каждое изменение пишется в той же транзакции, что и данные.
- Отправка идемпотентна: `UNIQUE (sender_id, client_id)`.
- Межпроцессная доставка — `LISTEN/NOTIFY` Postgres → `server.publish`. Redis не используем.
- Клиент: данные в SharedWorker (запасной путь — Dedicated Worker + Web Locks + BroadcastChannel), IndexedDB — локальный источник, главный поток — зеркало видимого и состояние интерфейса.
- Связь UI ↔ воркер — пять видов живых подписок: `chatList`, `messages`, `entity`, `search`, `counters`; патчи пачкой не чаще раза в 16 мс.
- Прочтение — монотонный указатель `last_read_id`; главный поток сообщает «вижу до id N», воркер сводит и схлопывает, сервер хранит `GREATEST`.
- Текст сообщений никогда не попадает в `innerHTML`; сессия — httpOnly-cookie.
- Тесты: `bun test`; серверные — на настоящем Postgres в Docker; воркер — с `fake-indexeddb`; UI — Playwright.

## Этапы

### Этап 1. Серверное ядро — `2026-10-16-relay-server-core.md`
**Результат:** в Docker поднимаются Postgres и сервер; два пользователя по WebSocket обмениваются сообщениями, догоняют журнал через `sync`, отмечают прочтение.
- Монорепо, Docker Compose (postgres, migrate, server, test), миграции.
- Схема: users, sessions, chats, chat_members, messages, user_seq, updates.
- Домен: `fanOut`, `getUpdates`, `sendMessage` (идемпотентно), `markRead` (монотонно, `readOwn`/`readBy`), список чатов, история.
- WebSocket-протокол `hello`/`sync`/`send`/`read`, `poke` через LISTEN/NOTIFY, dev-вход.

**Приёмка:** `docker compose run --rm test` зелёный; сценарий «A отправил → B получил poke → sync вернул newMessage → B прочитал → A получил readBy» проходит в интеграционном тесте.

### Этап 2. Движок синхронизации в воркере — `packages/sync-engine`
**Результат:** headless-клиент, который держит базу в IndexedDB, синхронизируется с сервером этапа 1 и выдаёт патчи по подпискам.
- Store (сущности, индексы, LRU, отложенная запись пачками в IDB), `lastSeq` в той же транзакции.
- SyncEngine: соединение, переподключение с нарастающей задержкой, `hello`/`sync`, обнаружение дыр в `seq`, `tooLong` → снимок.
- Outbox: `pending` → `ack` → `sent`, повторы, `failed`, порядок внутри чата.
- ReadTracker: `seen` → локальный пересчёт → `pendingReads` → схлопнутый `read`.
- Подписки и патчи (`snapshot`/`upsert`/`remove`/`move`), таблица инвалидации.
- Хосты: SharedWorker и запасной Dedicated + Web Locks.

**Приёмка:** тесты движка с `fake-indexeddb` против настоящего сервера в Docker: офлайн-отправка доходит после переподключения, дыра в журнале закрывается, две «вкладки» видят одно состояние.

### Этап 3. Веб-клиент: оболочка и список чатов — `apps/web`
**Результат:** открываешь страницу — мгновенно виден список чатов из кэша, приходят новые сообщения, работает офлайн-баннер.
- Сборка Bun, раздача статики сервером, сервис `web` в compose.
- Главный поток: `GlobalState`-зеркало, RPC к воркеру, `options.debounceRendering = requestMutation`, применение патчей с `deferDuringAnimation`.
- Relay: `FloatShell`, `SidebarCard`, `FolderTabs`, `FlipList`, `ChatRow`, `SyncIndicator`, `Banner`, обои.
- Холодный старт из IDB, затем синхронизация.

**Приёмка:** Playwright: первый кадр списка без сети; пришедшее сообщение поднимает чат наверх; офлайн-баннер появляется и исчезает.

### Этап 4. Лента и переписка
**Результат:** полноценная переписка: отправка, статусы, история, прочтение, ответы, реакции, правки, удаление, поиск по чату.
- `VirtualList` с якорем прокрутки, подгрузка истории, `UnreadDivider`.
- `useReadTracker` (IntersectionObserver + фокус) → `seen`.
- Composer: черновики в воркер, ответы, упоминания; меню сообщения, реакции, выделение, удаление.
- Серверные операции `edit`/`delete`/`react` и их изменения в журнале.

**Приёмка:** Playwright с двумя контекстами браузера: галочки проходят все стадии; прочтение на одном «устройстве» гасит бейдж на другом.

### Этап 5. Медиа и голосовые
**Результат:** фото, видео, документы и голосовые: загрузка с прогрессом, превью, просмотрщик, запись.
- MinIO в compose, подписанные URL, загрузка частями, `complete`.
- Воркер: уменьшение картинки, `thumb`, волна голосового (`OfflineAudioContext`).
- `MediaBubble`, `FileBubble`, `VoiceMessage`, `VoiceRecorder`, `MediaViewer`; Cache Storage для блобов.

**Приёмка:** загрузка переживает обрыв сети; голосовое проигрывается у получателя с волной.

### Этап 6. Пуши, поиск, превью ссылок, большие группы
- Web Push (VAPID) при отсутствии живого сокета.
- Полнотекстовый поиск (`tsvector`) + локальный индекс в воркере.
- Превью ссылок на сервере с защитой от SSRF.
- `chat_seq`/`chat_updates` для групп больше ~200 участников, без отчётов о прочтении.
- Ночная чистка журнала, `tooLong`.

**Приёмка:** нагрузочный тест: группа на 1000 участников, отправка не создаёт 1000 записей журнала; клиент, отставший больше чем на 30 дней, восстанавливается через снимок.
