# Безопасность: H1 (ключи доступа к людям) и M1–M5 — план

Основа: аудит `docs/security-audit-2026-10-31.md`. Для каждой находки сверено, как то же устроено в
Telegram — по двум веб-клиентам (tweb `~/Documents/tweb`, telegram-tt `~/Documents/telegram-dd`) и по
схеме MTProto, которую они несут. Код tweb/tt под GPL: здесь только поведение и имена методов API.
Сервер Telegram закрыт; то, что выведено из поведения клиентов, помечено «(вывод)».

Решение по H1 принято: **вариант А — ключ доступа к человеку, как `access_hash`**.

---

## H1. Ключ доступа к человеку (`peerKey`)

### Как в Telegram
- К пользователю обращаются только парой `inputUser { user_id, access_hash }` (так же `inputPeerUser`,
  у каналов `inputChannel`). Неверный хэш — `PEER_ID_INVALID` / `USER_ID_INVALID`.
- `access_hash` у каждого зрителя свой (вывод: хэш, полученный аккаунтом A, у аккаунта C не работает).
  Подделать нельзя, хранить на сервере не нужно.
- Выдаёт его только сервер — там, где человек виден законно: диалоги, сообщения, контакты,
  `contacts.resolveUsername`, поиск по телефону с учётом приватности, участники группы.
- Клиенты хранят хэш рядом с пользователем: tweb — в объекте `User` (`appUsersManager.getUserInput`),
  tt — `localDb.users[id].accessHash` (`buildInputUserFromLocalDb`; хэша нет — запрос не строится).
- «Неполные» пользователи (`min`) из больших групп и каналов: их хэш для большинства методов не годится,
  к ним обращаются через `inputUserFromMessage` — «автор сообщения N в чате X». tweb так и делает в
  `getUserInput` для `min`; tt не перезаписывает полную запись неполной.

### Как будет в Relay

**Ключ.** `peerKey(viewer, target) = base64url(HMAC-SHA256(secret, "peer:v1" ‖ viewer ‖ target)[0..12])`
— 16 символов. Секрет — новая строка `server_meta.peer_key_secret` (32 байта), по образцу
`deviceAuth.ts challengeSecret()`; при желании позже — через KMS, как `crypto/searchKey.ts`.
Проверка — пересчёт и `timingSafeEqual`. Состояния нет.

**Главное ограничение Relay.** Журналы групп и каналов общие: одно событие на чат уходит всем
подписчикам (`journal.ts:59-76`, `realtime.ts:93`, `chatJournal.ts:69` без зрителя). Значит, в
`newMessage`, `members`, `reactions`, `readBy`, `groupUpdated` ключ положить нельзя — там остаются
голые id. Это ровно телеграмовские `min`-пользователи. Ключ выдаётся только в ответах «на одного
зрителя»; голые id клиент и так добирает через `GET /users?ids=` (`engine.ts:995-1027`), а этот путь
уже фильтрует по `canView` (`users.ts:17-21`) — туда и кладём ключ.

**Где выдаём ключ** (везде, где строится `PublicUser` или частичный объект для одного зрителя):

| Место | Что добавить |
|---|---|
| `profile.ts:66 publicUser()` — единая точка `PublicUser` | поле `key` для зрителя |
| `GET /users/:id`, `GET /users?ids=` (`users.ts`) | через `publicUser` |
| `POST /users/resolve` (`contacts.ts:48 resolveUser`) | ключ — это и есть «знакомство по @имени/телефону» |
| контакты, чёрный список, `contactsChanged`, `blocksChanged` | через `publicUser` |
| `userUpdated` в личном журнале (`publishUser`, `republishUser`, `exchangeProfiles`) | ключ свой у каждого получателя: собирать запись под получателя (они уже пишутся по одной на зрителя) |
| список чатов `peer` (`chats.ts:273,329,374`, превью канала) | `peer.key` |
| `GET /search/people` (`globalSearch.ts:56`) | `key` в `PersonHit` |
| `GET /chats/:id/members`, `GET /groups/:id/members` | `key` у каждого участника (ответ на одного зрителя) |

**Где требуем ключ** — там, где проверки связи не было вовсе (сделано, ветка `fix/peer-keys`):

| Маршрут / кадр | Было | Стало |
|---|---|---|
| `POST /chats/direct` → `openDirect` | любой id | `{userId, key}` или `{userId, via}` |
| `POST /chats` → `createGroup` | `memberIds` | `members: [{id, key}]` |
| `POST /groups/:id/members` → `addGroupMembers` | `userIds` | `users: [{id, key}]` |
| WS `send {contact}` (карточка контакта) | любой id, имя в ответе | `{userId, key}` или `{userId, via}` |
| `GET /users/:id/music` | без проверки | `canView` |

`via: {chatId, messageId}` — «человек из этого сообщения», как `inputUserFromMessage`: зритель видит сообщение
(участник, не раньше `history_from`, не удалено), и оно называет человека — автор (не пост канала), «переслано от»
или карточка контакта. Так получатель карточки может написать человеку, которого иначе не видит.

**Контакты, блокировки, исключения приватности ключ не требуют:** они уже пускают только тех, с кем есть связь
(`canView` в `addContact`/`blockUser`, фильтр «контакт или общий чат» в `validRule`) и не отличают «нет человека» от
«не видно» — перебора там нет. Ключ для них — избыточен; можно добавить позже для единообразия.

**Ключ проверяется на границе** (HTTP-маршруты, WS-кадр), доменные функции по-прежнему принимают id — внутренние
вызовы и тесты домена не меняются.

Чтение профиля (`GET /users/:id`, фото, `common-groups`) остаётся под `canView`: ключ доказывает
«я законно узнал этого человека», а что из профиля показать — решает приватность сейчас.
`GET /users/:id/music` — добавить `canView` (сейчас нет вовсе, см. M1).

**Не требуем ключ** там, где цель обязана быть участником группы и это уже проверяется: удалить,
ограничить, звание, админ, передача прав, заявки (`groups.ts:420,444,462,490,537`, `invites.ts:142`).
`DELETE /blocks/:id`, `DELETE /contacts/:id`, `DELETE /groups/:id/bans/:uid` — только удаляют свою
строку и ничего не раскрывают.

**Ответ на неверный ключ** — тот же `404 not_found`, что и на несуществующего пользователя. Иначе
снова оракул перебора.

**Клиент.**
- Хранить `key` рядом с пользователем: `ProfileCache.users` (`sync-engine/profile.ts`, IDB `users`),
  `peer.key` в `LocalChat`, участники (`MembersCache`), контакты, блок-лист.
- Собирать запрос, как tt: нет ключа — сначала `GET /users?ids=` (получить ключ, если человек виден),
  потом действие; не видно — действие недоступно в UI.
- Места, которые шлют чужой id (по инвентаризации): `data.ts:1225 createDirectChat`,
  `data.ts:1235 createGroup`, `ui/group/Members.tsx:78`, `ui/newChat/NewChannel.tsx:107`,
  `sync-engine/contacts.ts:293`, `blocks.ts:176`, `engine.ts:1409 setPrivacy`, `engine.ts:2416`
  (карточка контакта).
- Старые записи в IndexedDB без ключа — дозапрос по `GET /users?ids=` при первом действии.

**Смена секрета.** Все ключи становятся недействительными. Клиент на `not_found` при действии с
человеком один раз дозапрашивает ключ через `GET /users?ids=` и повторяет.

**Не закрывается ключом, отдельная задача.** Тот, кто законно вас знает (общая группа, контакт),
всё ещё может добавить вас в новую группу. В Telegram для этого есть приватность «кто может
добавлять меня в группы» (`privacyKeyChatInvite`). Предлагаю следующим шагом.

### Задачи H1
1. Сервер: `crypto/peerKey.ts` — секрет, `peerKey(viewer, target)`, `checkPeerKey(viewer, target, key)`.
   Тесты: ключ A не подходит C; неверный и несуществующий — одинаковый ответ.
2. Выдача: `publicUser` + все места из таблицы «где выдаём». Протокол: поле `key` в `PublicUser`,
   `ChatSummary.peer`, `PersonHit`, участниках.
3. Требование: маршруты из таблицы «где требуем»; парсеры в `packages/protocol`.
4. Клиент: хранение ключа, дозапрос, перевод вызовов на `{id, key}`.
5. Тест-перебор: `POST /chats/direct` по диапазону id без ключа — все `404`, профили не открываются.

## M1. Музыка профиля

### Как в Telegram
- `account.saveMusic {id: InputDocument, unsave?, after_id?}` добавляет трек. `InputDocument` — это
  `id + access_hash + file_reference`; `file_reference` выдаётся сервером под контекст, где клиент
  получил документ. То есть добавить можно только документ, который вам законно пришёл (tweb
  `appSavedMusicManager` обновляет ссылку при `FILE_REFERENCE_EXPIRED` и повторяет).
- Профиль — новый контекст: зрители получают свежие ссылки через `users.getSavedMusic`, доступ решает
  отдельная приватность `privacyKeySavedMusic` (все / контакты / исключения). Доступ к треку в
  профиле не зависит от того, состоит ли владелец в исходном чате.
- tweb показывает «Добавить в профиль» только для настоящего аудиофайла и только если медиа можно
  сохранять (`canSaveMessageMedia` с учётом `noforwards` сообщения и чата). Не копировать: в tweb
  исключение для «не видео» пропускает аудио из защищённого чата — код и комментарий расходятся.
  Правильный предикат — как tt `selectIsMessageProtected`: защищено сообщение, или чат, или TTL.

### Варианты для Relay
- **А. Проверка при добавлении.** В `addProfileMusic` брать сообщение через `chat_members` с
  `m.id >= cm.history_from`; отказ для `protected` чата; убрать ветку `profile_music` из
  `attachmentForSend` (`files.ts:242`); `canView` для `GET /users/:id/music`. Маленько, но файл в
  профиле — всё ещё вложение из чата.
- **Б. А + своя копия.** При добавлении копировать объект в новое вложение владельца
  (`owner_id = userId`, без шифрования чата); `profile_music` указывает на копию, ветка
  `profile_music` в `fileFor` открывает только такие копии. Чат больше никогда не становится
  публичным, выход из чата и удаление сообщения ничего не ломают. Цена — место и миграция старых строк.
- **В. Перепроверка источника при каждой отдаче.** Хранить исходный чат и сообщение, в `fileFor`
  проверять, что владелец всё ещё их видит. Горячий путь тяжелее, профиль тихо ломается после выхода.

**Рекомендация:** А сразу, потом Б. Отдельно — приватность «кто видит мою музыку», как у Telegram.

## M2. Перебор пароля 2FA

### Как в Telegram
- Передача прав — `messages.editChatCreator {peer, user_id, password: InputCheckPasswordSRP}`.
- tt сначала зовёт её с `inputCheckPasswordEmpty` — как проверку условий: `PASSWORD_HASH_INVALID`
  значит «условия выполнены, спросите пароль», а `PASSWORD_MISSING`, `PASSWORD_TOO_FRESH_X` (пароль
  моложе 7 дней), `SESSION_TOO_FRESH_X` (сеанс моложе 24 часов) — отказ с таймером. То есть сервер
  проверяет наличие пароля, его возраст и возраст сеанса до самого пароля.
- Ошибки перебора — `FLOOD_WAIT_X`, `PHONE_PASSWORD_FLOOD`; клиенты показывают их одинаково при любом
  методе (вывод: счётчик общий на аккаунт, а не на метод).
- Оба клиента перед каждым доказательством заново берут `account.getPassword` (новый `srp_id`).

### Что ещё нашлось в Relay
Не только передача прав: `setPassword` и `removePassword` тоже зовут `verifyProof` без счётчика (их
закрывает только `assertConfirmed`, т. е. подтверждённая украденная сессия перебирает без лимита).
Плюс боковой путь: владелец выходит из группы — права сразу уходят старейшему админу
(`removeGroupMember`, `groups.ts:405-414`) без пароля; в Telegram это «станет владельцем через 7 дней,
если прежний не вернётся» (`messageActionNewCreatorPending`).

### Варианты для Relay
- **А. Общий счётчик на аккаунт.** Таблица `password_attempts(user_id, at, ok)` и одна функция
  `verifyProofLimited(userId, proof)` для всех проверок: вход (`checkPending`), передача прав,
  `setPassword`, `removePassword`. Превышение — `flood` с секундами, как `FLOOD_WAIT`.
- **Б. Счётчик только в передаче прав.** Меньше всего кода, но `setPassword`/`removePassword` открыты.
- **В. А + условия Telegram для передачи прав.** `assertConfirmed` (сеанс не свежий), пароль старше
  7 дней (`user_passwords.updated_at` → новая ошибка `password_too_fresh`), проверка условий до
  запроса пароля (как пустой пароль в tt), и выход владельца — отказ, пока есть админы, или отложенная
  на 7 дней передача.

**Рекомендация:** В на основе А.

## M3. Свежий сеанс и необратимые действия

### Как в Telegram
| Ошибка | Где | Смысл |
|---|---|---|
| `FRESH_RESET_AUTHORISATION_FORBIDDEN` | `auth.resetAuthorizations`, `account.resetAuthorization` | нельзя завершать сеансы из свежего |
| `FRESH_CHANGE_AUTHORIZATION_FORBIDDEN` | `account.changeAuthorizationSettings` | то же для подтверждения |
| `SESSION_TOO_FRESH_X` | передача прав, вывод Stars/подарков | сеанс моложе 24 ч |
| `PASSWORD_TOO_FRESH_X` | те же | пароль моложе 7 дней |

Удаление канала (`channels.deleteChannel`), удаление переписки у обоих (`messages.deleteHistory
revoke`), смена @username — в Telegram **без** пароля и без проверки свежести, только диалог
подтверждения (tt `DeleteChatModal`, tweb `popups/deleteDialog`).

### Почему Relay должен быть строже
У Relay удаление группы и чата «у обоих» уничтожает ключи шифрования (crypto-shred) — восстановить
нельзя даже из бэкапа. У Telegram такой необратимости нет.

### Варианты для Relay
- **А. `assertConfirmed` внутри транзакции** для: `deleteGroup`, `transferGroupOwnership`, снятия или
  замены публичного @username группы (`setGroupUsername`) и своего (`profile.setUsername`),
  `deleteDirectChat` при `forAll`, выхода владельца (`removeGroupMember`). Для этого `groupRoute`
  получает `sessionId` (сейчас только `userId`). Ошибка — уже существующая `fresh_session` (403), у
  клиента для неё есть текст. Вызов именно внутри `sql.begin`: `assertConfirmed` берёт `for update`
  (в `http.ts:241` сейчас без транзакции — поправить заодно).
- **Б. Только передача прав и выход владельца** — точно как Telegram. Свежий украденный сеанс по-прежнему
  уничтожает группы и чаты.
- **В. А + пароль 2FA для удаления группы/канала**, если пароль включён. Строже Telegram, лишнее
  трение, ещё один путь перебора (нужен счётчик из M2).

**Рекомендация:** А. Новый @username ставить можно и из свежего сеанса — ограничиваем только снятие.

## M4. Push-подписка как SSRF

### Как в Telegram
- tweb (`webPushApiManager`) и tt (`methods/settings.ts`) отправляют `account.registerDevice
  {token_type: 10, token: JSON подписки (endpoint, keys), secret?, no_muted}`; `secret` — ключ
  повторного шифрования, если стоит код-пароль.
- Белого списка хостов в клиентах нет — проверяет сервер, ошибки в схеме `TOKEN_INVALID`,
  `TOKEN_TYPE_INVALID`. Что именно проверяет сервер, снаружи не видно.

### Реальные push-сервисы браузеров
Chrome и Chromium-браузеры — `fcm.googleapis.com` (раньше `android.googleapis.com`);
Firefox — `updates.push.services.mozilla.com`; Safari 16+ — `web.push.apple.com`;
Edge — `*.notify.windows.com`.

### Ещё одна деталь в Relay
`deliverPush` идёт по редиректам (`fetch` без `redirect: 'manual'`) — внешний хост может отправить
воркер на внутренний адрес ответом 3xx. Закрыть при любом варианте.

### Варианты для Relay
- **А. Белый список хостов** при подписке и повторно при доставке: точные хосты выше и
  `*.notify.windows.com`; только `https`, порт по умолчанию, без `user@`; список настраивается
  (`PUSH_ALLOWED_HOSTS`). Закрывает SSRF полностью, включая трюки с DNS. Минус — новый push-сервис
  требует правки списка.
- **Б. Общий безопасный `fetch` из превью ссылок** (`resolvePublic` + подключение к проверенному IP,
  вынести в `net/safeFetch.ts`), порт 443, без редиректов. Работает с любым сервисом, но разрешает
  слать мусор на любые публичные хосты от имени сервера.
- **В. А + Б.** Список и проверенный публичный IP.

**Рекомендация:** В (минимум — А). Неподходящий адрес — понятная ошибка при подписке
(«уведомления в этом браузере не поддерживаются»), как `TOKEN_INVALID`. Исключение `http` в dev —
только для localhost.

## M5. Гонка счётчиков попыток

### Как в Telegram
Оба клиента перед каждым паролем заново получают `account.getPassword` и никогда не переиспользуют
`srp_id` (tt `client/auth.ts signInWithPassword`, `2fa.ts`; tweb после ошибки перечитывает состояние и
опрашивает каждые 10 с). tt обрабатывает `SRP_ID_INVALID`. Вывод: у аккаунта один текущий `srp_id`,
а не сколько угодно параллельных вызовов — число одновременных попыток ограничено.

### В Relay
Вызов SRP уже одноразовый (`verifyProof` удаляет его), но выдаётся без ограничений — N вызовов, N
доказательств разом, и все видят «ошибок < 10».

### Варианты для Relay
- **А. Сначала занять попытку, потом проверять.** В `checkPending`: атомарный
  `update login_pending set tries = tries + 1 where id = … and dead_at is null and tries < 5 returning`;
  нет строки — вход мёртв. В той же транзакции запись в общий счётчик из M2 под
  `pg_advisory_xact_lock` по пользователю. Потом `verifyProof`. `finishRecovery` — так же одним
  `update … returning`.
- **Б. Замок по пользователю вокруг «прочитать → проверить → записать».** Легко встроить, но
  сериализует вычисление SRP и всё равно полагается на чтение.
- **В. Один живой вызов на пользователя, как один `srp_id`.** `challengeFor` удаляет прежние вызовы
  пользователя перед новым. Две вкладки отменяют вызовы друг друга — клиент просто берёт новый, как tt
  и tweb.

**Рекомендация:** А + В. А делает счётчики точными, В повторяет модель Telegram и заодно ограничивает
перебор в M2.

## Порядок работ

1. **H1** — ключи доступа (самое большое: сервер, протокол, клиент).
2. **M3** — `assertConfirmed` на необратимых действиях (маленькое, закрывает уничтожение данных).
3. **M2 + M5** — общий счётчик пароля, атомарные попытки, один живой вызов, условия передачи прав.
4. **M4** — белый список push-хостов, проверенный IP, без редиректов.
5. **M1** — проверки при добавлении музыки (А), затем копии (Б) и приватность музыки.

Каждый пункт — отдельная ветка с тестами на сервере (`docker compose --profile test run --rm test`)
и проверкой в Chrome там, где меняется UI.
