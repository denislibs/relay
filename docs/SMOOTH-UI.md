# Плавный интерфейс: правила Relay

Главное требование к клиенту — плавность. Пользователь не должен видеть вспышек, рывков и «подвисаний».
Правила ниже выведены из реальных замеров, в первую очередь перехода по стеку чатов (`ChatStack`, `data.ts`).
Сделали иначе — докажите замером, что не хуже.

## Цели в цифрах

- Во время анимации каждый кадр не длиннее 8–9 мс при 120 Гц (16 мс при 60 Гц). Длинных задач (> 50 мс) нет.
- От действия пользователя до видимого отклика — меньше 100 мс. Для частых действий, вроде открытия чата из
  списка, — меньше 40 мс.
- Ни одного кадра с «пустым», «нет сети» или прыгнувшей прокруткой.

## 1. Кадр: чтение и запись раздельно

- Раскладку читают в `requestMeasure`, DOM меняют в `requestMutation` (`packages/relay-ui/src/schedule.js`).
  Чтение после записи в той же фазе вызывает принудительную раскладку.
- `forceMeasure` — только осознанно, когда позицию надо поправить до отрисовки (якорь ленты). Одно чтение и одна
  запись, с комментарием, почему так.
- В dev-сборке нарушения ловит `strict.js`. Предупреждение `[strict-dom]` считается ошибкой.

## 2. Состояния и загрузка

- Лоадер появляется не сразу (≈ 150 мс задержки) и держится не меньше ≈ 600 мс. Иначе он мигает.
- Смена состояний (скелет → содержимое, одна вкладка → другая) — через crossfade, без пустого кадра между ними.
- Первым показываем то, что уже есть на устройстве (IndexedDB), а не «загрузку».

## 3. Переходы: готовить заранее, переключать одним кадром

Образец — стек чатов. Так же делает Telegram Web.

1. **Готовить скрыто и заранее.** Новый экран рендерится и раскладывается в скрытом виде (`visibility: hidden`,
   `inert`) до начала анимации. Если можно предугадать действие, начинать подготовку на нажатии:
   `pointerdown` готовит, `click` переключает, без клика заготовка выбрасывается (`ui/press.ts`). Только для мыши:
   на тач-экране нажатие — часто начало прокрутки.
2. **Переключение — только смена классов.** Тяжёлый рендер и старт анимации никогда не идут в одном кадре:
   сначала содержимое, следующим кадром (или в ближайшей фазе записи, если уже разложено) — классы.
3. **Одна точка переключения.** Все движущиеся части получают новые классы из одного состояния в одном рендере.
   Никаких собственных флагов «я готов» через `requestAnimationFrame` у каждой колонки: из-за них старый экран
   уезжал на 70 мс раньше, чем появлялся новый.
4. **Честное окно анимации.** На время перехода включается `beginHeavyAnimation(длительность + запас)`. Всё, что
   не участвует в анимации, ждёт `onHeavyAnimationEnd`: боковые панели (`useSettled` в `Info.tsx`), дорисовка
   истории, загрузка медиа, сетевые запросы панелей.
5. **Анимировать только `transform` и `opacity`.** `will-change` — только на готовящемся элементе и на время
   перехода, потом снять: постоянный слой на весь экран — лишняя память видеокарты.
6. **Не пересоздавать то, что уже есть.**
   - Ключи Preact действуют только внутри одного массива. Элемент, который переходит из одного списка в другой
     (стек → уходящие), рендерить одним общим массивом, иначе он размонтируется и соберётся заново.
   - Недавно закрытые экраны держать живыми и скрытыми (стек чатов: до минуты, не больше двух). Повторное
     открытие — только анимация.

## 4. Лента и списки

- В DOM — только окно сообщений. Списки чатов виртуальные (`WindowList`).
- Первый экран — порцией (`FIRST_PAINT` = 24). Остальное — после анимации, порциями (`FILL_CHUNK` = 16 строк
  за кадр). Якорь (первая видимая строка) восстанавливается на каждой порции: эффект с якорем зависит от лимита
  показанных строк, а не от флага «частично».
- `content-visibility: auto` в ленте с якорями не использовать: оценочные высоты сдвигают прокрутку, выигрыша
  в замере нет.
- Плавная прокрутка ленты (новое сообщение у низа, «вниз», переход к сообщению) — только через `scrollDrive.ts`:
  свой тайминг, цель читается каждый кадр, поездка под `beginHeavyAnimation`, первый ввод пользователя её обрывает;
  `behavior: 'smooth'` в ленте не используется. Без анимаций и в скрытой вкладке — мгновенно.
- Удаление сообщения на экране — FLIP соседей (`leaving.ts`): уходящая строка ещё один рендер стоит на месте, потом
  выводится из потока (`position: absolute`) и гаснет, соседи доезжают `transform`-переводом 220 мс. Высоту не
  анимируем. Одно чтение раскладки и одна запись в `forceMeasure` — осознанное исключение, с комментарием в Feed;
  куда сдвинутся соседи, считается из снятых прямоугольников, а не перемеряется (второй принудительный пересчёт
  стоил кадра). Метки `relay:leave-measure` / `relay:leave-start` — во вкладке Performance.
- Ленивые картинки: корень наблюдателя — сам прокручиваемый контейнер (`LazyRoot`), не окно: с корнем-окном строки,
  обрезанные прокруткой, в зону запаса не попадают вовсе. В зоне запаса (500 px) `fetchpriority=low`, в экране —
  `high`: браузер отдаёт полосу видимому (как очередь «видимое вперёд» в Telegram, без своей очереди). В скрытой
  вкладке `decode()` не ждём.
- Якорь сдвига окна держится за край по правилу Telegram Web K (`anchorShift`): обычно верх первой видимой
  строки; строка торчит за верх экрана — её низ; торчит за оба края и свернулась — её верх к верху экрана.
- Позиция прокрутки чата (`pos:<chatId[:threadId]>` в `meta` IndexedDB движка) переживает перезагрузку: пишется через
  секунду после остановки прокрутки и при уходе со страницы, только если лента не внизу (внизу — запись стирается);
  при открытии окно запрашивается с якорем и приходит из кэша без сети.

## 5. Дешёвый рендер

- `Intl.*Format` и прочие форматтеры — создавать один раз и кэшировать, не на каждый пузырь.
- Закрытые модалки и панели (календарь, просмотрщики) не монтировать до первого открытия.
- Первая инициализация тяжёлых API браузера — не в обработчике действия. Пример: первый `new AudioContext()` на
  странице синхронно поднимает аудиосервис (250–600 мс) — короткие звуки играют через `<audio>`, вывод заводится
  заранее, в простое (`sound.ts`). Холодный старт проверять в свежем профиле браузера: в «тёплом» его не видно.
- Строки ленты — `memo`. Не создавать новые объекты и функции в пропсах горячих строк без нужды.

## 6. Замер обязателен — до и после

- **Покадровый сэмплер в странице.** В каждом `requestAnimationFrame` пишем длительность кадра, `transform`
  анимируемых элементов, `PerformanceObserver('longtask')` и при нужде `MutationObserver`. Из этого видны:
  время от действия до старта, рассинхрон частей, длинные кадры, лишние изменения DOM во время анимации.
- **Трасса Chrome** — чтобы понять, *что* делает длинная задача. CPU-профиль по функциям, строки сборки
  сопоставляются с исходниками через sourcemap.
- **Несколько прогонов (5+).** Единичные кадры по 25–60 мс без длинных задач и без изменений DOM — это шум
  машины (≈ 1%), а не код.
- **Итог — по продакшен-сборке.** В dev добавляются `strict.js` и неминифицированный код. Если общая рабочая
  копия не собирается из-за чужой работы — собрать свою правку в чистой копии (`git worktree` + `WEB_OUT=…
  bun apps/web/build.ts`) и поднять второй nginx на `https://localhost:8443` с тем же API.
- **Отметки `performance.measure`** в коде данных (например, `relay:feed-snapshot`) видны во вкладке Performance.

### Сэмплер (вставить в консоль, вызвать `rec(() => действие())`)

```js
const rec = (act, ms = 900) => new Promise((done) => {
  const frames = [], lts = [];
  const lo = new PerformanceObserver((l) => l.getEntries().forEach((e) => lts.push(Math.round(e.duration))));
  lo.observe({ type: 'longtask' });
  const t0 = performance.now(); let last = t0;
  (function f(now) {
    const xs = [...document.querySelectorAll('.app-chatcol')]
      .map((c) => Math.round(new DOMMatrix(getComputedStyle(c).transform).m41));
    frames.push([Math.round(now - t0), Math.round(now - last), xs.join(',')]); last = now;
    if (now - t0 < ms) requestAnimationFrame(f); else { lo.disconnect(); done({ frames, lts }); }
  })(t0);
  act();
});
```
