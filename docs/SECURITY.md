# Безопасность Relay

Как Relay защищает переписку, файлы и сеансы, от чего именно и где граница этой защиты.
Подробный план и история этапов — `docs/plans/2026-10-21-relay-at-rest-encryption.md`.

## Модель угроз

Relay — не мессенджер со сквозным шифрованием (E2E). Сервер в момент работы может прочитать переписку: ему это
нужно для поиска, превью ссылок, push-уведомлений и синхронизации между устройствами. Цель другая:

**утечка любого одного компонента не раскрывает переписку и файлы.**

| Что утекло | Что видит злоумышленник |
|---|---|
| Дамп базы или бэкап данных | метаданные (кто, кому, когда, размеры); тексты и черновики — шифр |
| Бакет S3 | шифр файлов; имён, типов и содержимого нет |
| Индекс поиска | индекс во внутренней сети, без бэкапа; у сервера ключ только на поиск |
| Трафик внутри кластера | TLS между всеми сервисами |
| Cookie сеанса (вредонос, копия профиля браузера) | не больше 10 минут доступа: обновить его без ключа устройства нельзя |
| Бэкап, сделанный до удаления чата | старый шифр, ключи к которому уничтожены |

**Чего мы не обещаем:**
- работающий сервер с доступом к KMS читает переписку;
- метаданные видны;
- веб-клиент доверяет коду, который ему отдал наш сервер.

## Принципы

- **Никакой своей криптографии.** Только WebCrypto: AES-256-GCM, HKDF-SHA256, ECDSA P-256 и HMAC.
- **Шифр описывает сам себя.** В нём записаны версия формата и версия ключа: ключи и формат можно менять без
  остановки сервиса.
- **Переходный режим на каждом этапе.** Старое читается, новое пишется по-новому, фоновая задача догоняет.
- **Dev без внешних сервисов.** Поддельный KMS (`FakeKms`); настоящий путь через OpenBao тоже проверяется тестами.

## Ключи

```
главный ключ (KEK) ── только внутри KMS (Vault / OpenBao Transit), наружу не выходит
   └─ заворачивает ключи чатов и файлов (DEK) ── схема keys в Postgres, только в завёрнутом виде
         ├─ keys.chat_keys        — ключ чата по версиям
         └─ keys.attachment_keys  — ключ файла (нужен воркеру для превью и перекодирования)
```

- Развёрнутые ключи живут только в памяти процесса, в кэше. Удаление ключа рассылается через `NOTIFY` и чистит кэш
  всех процессов.
- **Сервис ключей** (`apps/server/src/keyService.ts`) — единственный процесс с учётными данными KMS:
  - server и worker обращаются к нему по своим токенам (`KMS_PROVIDER=service`);
  - каждое обращение пишется в журнал аудита — **цепочку с HMAC** (`apps/server/src/auditLog.ts`): у записи номер,
    хэш предыдущей и HMAC ключом `KEY_SERVICE_AUDIT_KEY`. Удалённая, вставленная, переставленная или исправленная
    запись находится проверкой (`bun apps/server/src/auditVerify.ts audit.log`); без ключа цепочку не подделать.
    Записи идут и в файл, и в stdout (во внешний сбор логов: отправленное не переписать); раз в минуту — heartbeat,
    обрезанный хвост виден по разрыву во времени;
  - число развёртываний в минуту ограничено, при превышении — отказ и тревога.
- **Смена главного ключа:**
  - `RELAY_MASTER_KEY_PREVIOUS` или новая версия ключа в Transit;
  - задача `crypto.rewrap` перезаворачивает ключи чатов;
  - старый шифр сообщений перешифровывать не нужно.

## Сообщения и черновики

- **Где лежит.** Текст, разметка, превью ссылки, чек-лист, статья и метаданные вложения хранятся в
  `messages.content`; черновики — в `drafts.content`.
- **Формат:** `[формат][версия ключа][nonce 12 байт][шифр + тег]`.
- **AAD** = `messages|<чат>|<client_id>|content`. Шифр, перенесённый в другую строку или поле, не откроется.
- **Журнал `updates` и задачи `jobs`** хранят только ссылки `{chatId, id}`. Тела подставляются при выдаче `sync`,
  поэтому текст в них не дублируется.
- **Поиск:**
  - Meilisearch изолирован и **не хранит текст**: вместо слов — HMAC-токены (`apps/server/src/search/tokens.ts`):
    каждое слово и его префиксы (2…20 букв) → HMAC-SHA256 ключом поиска (`keys.search_key`, завёрнут KMS).
    Утечка индекса даёт только «какие сообщения содержат одно и то же слово». Цена: опечатки не прощаются;
  - запрос превращается в те же токены; найденные id сервер перепроверяет и открывает в Postgres;
  - запасной поиск по Postgres расшифровывает и проверяет не больше 5000 строк;
  - признак «есть ссылка» (`has_link`) остаётся открытым, чтобы работала вкладка «Ссылки».
- Код — `apps/server/src/domain/messageContent.ts` и `apps/server/src/crypto/`.

## Файлы

Файл шифрует клиент до загрузки. В S3 попадает только шифр. Формат RLF1 (`packages/protocol/src/fileCrypto.ts`):

```
заголовок 24 байта: 'RLF1' | размер куска | исходный размер | основа nonce (8 байт, случайная)
куски по 512 КБ:    AES-256-GCM, nonce = основа ‖ номер куска, AAD = «relay-file|номер|последний»
```

- **Целостность.** Номер куска в nonce и AAD не даёт переставить куски. Признак «последний» не даёт незаметно
  обрезать файл.
- **Ключ файла:**
  - получатели узнают его из шифра сообщения;
  - воркер берёт его из `keys.attachment_keys`;
  - копии (превью, 720p) шифруются ключами, выведенными через HKDF, и своих ключей не хранят.
- **Расшифровка в браузере.** Её делает Service Worker, по кускам и с поддержкой Range: видео перематывается, начало
  кэшируется. На устройстве ключи файлов лежат в IndexedDB `relay-attachments-on-device` (хранилище `file_keys`);
  при выходе они удаляются.
- **Не шифруются** аватарки, обои и музыка профиля: они публичны по смыслу.

## Удаление (crypto-shredding)

- **«Удалить у всех» и удаление чата** уничтожают ключи старых версий. Новые сообщения пишутся следующей версией
  ключа.
- **Бэкапы разделены** (`tools/backup/pg-backup.sh`):
  - данные без схемы `keys` хранятся 30 дней;
  - ключи отдельно — 7 дней.

  Через 7 дней удалённое не восстановить даже из бэкапа данных.

## Транспорт

Транспорт описан в `apps/server/src/tls.ts`.

- **Postgres:** `DB_SSL=verify-full`, клиентский сертификат (mTLS), в `pg_hba` только `hostssl`.
- **Valkey:** `rediss://`.
- **S3, KMS, поиск, сервис ключей:** https.
- **В production** (`NODE_ENV=production`) процесс без TLS не стартует; поддельный KMS там
  не запускается, если не задан явный обход `RELAY_ALLOW_FAKE_KMS` (только для стендов).

## Сеансы

### Вход

Варианты: код в служебный чат «Relay» на уже вошедших устройствах (SMS-доставки пока нет), облачный пароль по SRP (сам пароль серверу не передаётся), passkeys и
восстановление через почту. Сеансы истекают при неактивности (срок задаётся в настройках); список сеансов и их
завершение есть в настройках.

- **«Новый вход»** в служебный чат — только если есть кому ответить (другое подтверждённое устройство): устройство,
  **место по IP** (страна и город, `apps/server/src/geoip.ts`, база DB-IP Lite / GeoLite2 — `tools/geoip/fetch.sh`,
  путь `GEOIP_DB`), IP, время, **способ входа** (код, код и пароль, восстановление, паскей, QR). Страны входа нет ни у
  одного другого сеанса — пометка **«Необычное место»**. Кнопки «Это я» / «Завершить» — только на подтверждённом
  другом устройстве.
- **Ограничения нового сеанса** (как в Telegram): первые сутки (`restricted_until`), а вход по коду — пока его не
  подтвердят (до недели), нельзя завершать и подтверждать другие сеансы, впускать устройства по QR, менять пароль,
  почту восстановления и паскеи. «Это я» с другого устройства снимает ограничение. Первому устройству аккаунта и
  входу по QR (его впустило вошедшее устройство) ограничений нет.
- **Коды входа** — под спойлером; после входа или новой попытки цифры в сообщении скрываются («Код использован для
  входа» / «Код заменён новым»): новое устройство не прочтёт старые коды из истории.
- **В сеансе хранится:** устройство (браузер, ОС), строка браузера, IP, страна и город, способ входа, ключ
  устройства, время входа и последней активности.

### Сеанс, привязанный к устройству

Цель — украденный cookie сам по себе бесполезен.

1. При входе браузер создаёт **неизвлекаемый** ключ ECDSA P-256 и хранит его в IndexedDB `relay-device`
   (`packages/sync-engine/src/device.ts`). Закрытую часть нельзя прочитать даже из JavaScript страницы.
2. Любой вход (код, пароль, восстановление, регистрация, паскей, QR) присылает ключ с подписью
   «relay-device|bind|вызов» — сеанс **создаётся уже привязанным** и сразу получает короткий доступ: его долгий cookie
   без ключа бесполезен с первого запроса.
   - **Паскей:** ключ устройства записан вместе с вызовом WebAuthn — подпись паскея впускает именно это устройство,
     другой ключ на завершении отклоняется.
   - **QR:** ключ записан при создании кода — забрать вход может только создавшее его устройство, а не тот, кто
     подсмотрел или сфотографировал QR.
   - Сеансы, созданные старым клиентом без ключа, привязываются при первом обновлении доступа:
   - `GET /session/challenge` возвращает вызов: HMAC, действует 2 минуты;
   - `POST /session/refresh` принимает подпись строки «relay-device|refresh|вызов».
3. После привязки разделяются два cookie:
   - долгий `relay_session` ничего не открывает;
   - API требует короткий `relay_access` (10 минут);
   - без него сервер отвечает `401 {code:'access_expired'}` с заголовком `x-relay-auth: refresh`.
4. Обновление доступа:
   - **заранее:** страница обновляет его раз в 4 минуты и при возврате на вкладку;
   - **по требованию:** движок, страница и Service Worker при таком ответе подписывают вызов и повторяют запрос.
     Экрана входа и стирания данных при этом нет.
5. **WebSocket** привязанного сеанса:
   - присылает `{op:'challenge'}`;
   - кадры клиента ждут в очереди до `{op:'prove', sig}` (подпись «relay-device|ws|вызов»);
   - неверная подпись или 10 секунд без неё — закрытие с кодом 4401.
6. При выходе ключ устройства удаляется; следующий вход привяжет новый.

Сервер — `apps/server/src/deviceAuth.ts` и `auth.ts`; клиент — `device.ts` в движке, `apps/web/src/deviceAuth.ts`.

## Страница: CSP, Trusted Types, целостность сборки

Ключ устройства не извлекается, но пользоваться им может любой скрипт страницы — поэтому чужой скрипт не должен
на неё попасть.

- **Content-Security-Policy** (`docker/nginx/security-headers.conf`): скрипты — только файлы своего origin
  (встроенных нет: `boot-<хэш>.js` вместо inline), без `eval` (`'wasm-unsafe-eval'` — только WASM tlottie);
  медиа — свои, `blob:`/`data:` и хранилище S3; `frame-ancestors 'none'`, `object-src 'none'`, `base-uri 'none'`.
  Шрифтов и скриптов со сторонних серверов нет.
- **Trusted Types** (`require-trusted-types-for 'script'`): строка в `innerHTML`, `DOMParser`, адрес воркера или
  Service Worker проходит политику:
  - `default` (`apps/web/src/trustedTypes.ts`) — HTML через DOMPurify (без `<script>`, `on*`, `javascript:`),
    адрес скрипта — только свой origin, текст скрипта (`eval`, строковые таймеры) — никогда;
  - `relay-icons` (`kit.js`) — только константы иконок; `dompurify` — внутренняя политика DOMPurify.
- **Subresource Integrity:** у `boot`, `main` и стилей в `index.html` — `integrity="sha384-…"`.
- **Целостность в Service Worker:** `build.ts` зашивает в `sw.js` таблицу SHA-256 всех файлов сборки с хэшем в имени
  (`apps/web/src/buildIntegrity.ts`). Оболочка ставится и файл отдаётся странице только при совпадении байтов;
  иначе — ошибка загрузки. Подмена кода в CDN, HTTP-кэше или прокси не исполнится. Корень доверия — `index.html`
  и `sw.js` с нашего origin (без кэша).
- Прочие заголовки: `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`,
  `Cross-Origin-Opener-Policy: same-origin`, `Permissions-Policy` (камера и микрофон — только свои). В production —
  ещё HSTS.

## Конфигурация production

Overlay `docker-compose.secure.yml`:

| Сервис | Доступ |
|---|---|
| `keys` | единственный держатель `VAULT_TOKEN`; сети `keys` и `kms-egress`; журнал аудита — том `keys-audit` |
| `server` | `KMS_PROVIDER=service`, свой токен; поиск — `MEILI_API_KEY` (только поиск) |
| `worker` | `KMS_PROVIDER=service`, свой токен; пишет в индекс поиска |
| `search` | только внутренняя сеть, без бэкапа (индекс восстанавливается из базы) |

Обязательные переменные: `KEY_TOKEN_SERVER`, `KEY_TOKEN_WORKER`, `VAULT_ADDR`, `VAULT_TOKEN`, `MEILI_MASTER_KEY`,
`KEY_SERVICE_AUDIT_KEY` (32 байта, base64; копия — у того, кто проверяет журнал), `GEOIP_DB` (по желанию),
сертификаты TLS (`NODE_EXTRA_CA_CERTS` для внутреннего CA).

## Версии зависимостей

Версии образов закреплены. После бюллетеней безопасности сверять с ними (проверка 2026-10-31):

| Компонент | Версия | Почему |
|---|---|---|
| Bun | 1.4.4 | CVE-2026-111497 (brotli, RCE) — в 1.0.21–1.4.3 |
| nginx | 1.30.6, официальный образ + ngx_brotli (`docker/nginx/Dockerfile`) | октябрьские CVE 2026 в пакеты Alpine 3.21–3.23 не перенесены |
| OpenBao (dev/test) | 2.7.2 | исправления 2.6.3/2.6.4/2.7.1 |
| Valkey 8.1, SeaweedFS 4.48, PostgreSQL 17, Meilisearch 1.55 | — | известные исправления уже внутри |

Кроме обновлений — уменьшение поверхности: превью ссылок и push просят ответ без сжатия и ничего не распаковывают
(`decompress: false`; сжатый ответ сайта — «превью нет»), так что ошибка в распаковщике чужим сервером не
достигается. TLS session tickets выключены (`docker/nginx/nginx.conf`).

## Известные пробелы

- **Не E2E:** сервер с доступом к KMS читает переписку. Направление на будущее — секретные чаты и поиск на клиенте.
- **`style-src 'unsafe-inline'`:** встроенные стили разрешены (тема до загрузки CSS, акцентный цвет). Скрипт ими
  не запустить, но внедрённый CSS может менять вид страницы.
- **Метаданные открыты:** кто, кому, когда, размеры файлов.
