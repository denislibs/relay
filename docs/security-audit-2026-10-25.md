# Аудит безопасности Relay — 25 октября 2026

Внутренний аудит ветки `master` (коммит `2b33681`): код и живые атаки на локальный стенд.

## Как проводился

Пять независимых аудиторов (агентов без общего контекста), каждый на свой слой:

- вход и сеансы;
- права доступа (IDOR);
- криптография и ключи;
- веб-клиент;
- входные данные сервера и инфраструктура.

Каждый сверял код с [SECURITY.md](SECURITY.md) и проверял находки на стенде `https://localhost` на своих тестовых пользователях. Чужие данные никто не трогал.

Затем по каждому слою работал отдельный «скептик». Его задача — опровергнуть каждую находку: перечитать код и вызывающих, найти защиту в другом месте, воспроизвести атаку. Серьёзность он пересматривал честно. Ниже указана серьёзность **после** проверки. Все находки отчёта — подтверждённые, правдоподобных и опровергнутых не осталось.

Ограничение: это не замена независимому внешнему аудиту. Код писался в том же окружении.

**Что держится** (аудиторы искали и не нашли):

- XSS: имена, сообщения, статьи и ссылки рендерятся как текст или отбрасываются.
- Trusted Types, CSP, SRI и таблица целостности в Service Worker работают, как заявлено.
- Шифр сообщений устроен правильно: AES-256-GCM, случайный nonce на каждое поле. Формат файлов RLF1 не даёт переставить или обрезать куски.
- Выход и завершение сеанса действительно отзывают доступ.
- Вход по QR и паскею привязан к ключу устройства.
- Ограничения нового сеанса стоят на всех задокументированных путях.
- Лимиты кодов входа работают, ответы для несуществующих логинов не выдают, есть ли аккаунт.
- Права участников в основных путях выдаются по членству: история, медиа, кнопки, сеансы. Пересылка из защищённых чатов закрыта.

**Главные слабые места:**

1. Сокет до подписи ключом устройства — AUTH-1.
2. Скрытая история группы обходится через поиск, файлы и живые события — AUTHZ-1…4.
3. Crypto-shredding не доходит до файлов, индекса поиска и кэша превью — CRYPTO-1, 2, 4.
4. Production-конфигурация не соответствует обещаниям SECURITY.md — INFRA-1, 2, 3, 5.
5. SSRF в превью ссылок — SSRF-1, 2.

## 🔴 Критично

### AUTH-1. Сокет привязанного сеанса получает входящие сообщения до подписи ключом устройства
`apps/server/src/http.ts` (обработчик `open` WebSocket, ~448)

Для привязанного сеанса `/ws` открывается по одному долгому cookie и ждёт `prove`. Но в `open()` сокет **сразу** подписывается на `user:<id>` и `session:<id>`. В очередь до подписи попадают только кадры **от** клиента; всё, что сервер публикует пользователю, уходит неподтверждённому сокету. Это новые личные сообщения целиком, «печатает», присутствие. `subscribeUserSockets` тоже подписывает такие сокеты на новые группы.

- **Чем грозит.** Украденный долгий cookie без ключа устройства даёт бессрочный живой поток входящих сообщений: через 10 секунд сокет закрывается с 4401, после чего достаточно переподключиться. Ровно то, от чего должен был защищать этап 8.
- **Проверка.** Воспроизведено вживую: при открытом таким сокетом пришёл `newMessage` с текстом, потом `4401`.
- **Исправление.** До успешного `prove` не подписывать сокет ни на какие топики, не регистрировать его и не отмечать «в сети». Всё это делать после подписи и затем догонять журнал через `sync`. Проще всего не открывать `/ws` без действующего `relay_access`: клиент сначала обновит доступ.

## 🟠 Высокая

### AUTHZ-1. Поиск сообщений отдаёт скрытую историю
`apps/server/src/domain/search.ts:41`

Поиск (Meilisearch и запасной по Postgres) проверяет только членство и не смотрит на `chat_members.history_from`. Все остальные пути чтения — история, сообщения по id, медиа, дата, ветки — фильтруют `id >= history_from`.

- **Чем грозит.** Участник группы со скрытой историей полнотекстовым поиском читает сообщения, отправленные до его вступления. То же с личным чатом после «удалить у себя».
- **Проверка.** Воспроизведено: `/chats/:id/messages` скрывает сообщение, а `/search?q=…` отдаёт его целиком.
- **Исправление.** В проверке результатов и в запасном запросе добавить `and m.id >= cm.history_from`.

### AUTHZ-2. Глобальный поиск медиа и файлов обходит скрытую историю
`apps/server/src/domain/globalSearch.ts:37`

`searchMedia` не фильтрует по `history_from`.

- **Чем грозит.** Файлы, голосовые и ссылки до вступления в группу видны вместе с id вложений, а их можно скачать (см. AUTHZ-3).
- **Проверка.** Воспроизведено: `/search/media?kind=file` вернул сообщение до вступления, `/files/<id>` ответил 302.
- **Исправление.** Тот же фильтр, что в `getChatMedia`.

### CRYPTO-2. Файлы в чате после crypto-shredding остаются доступными
`apps/server/src/domain/files.ts:252`

Удаление «для обоих» уничтожает только версии ключа чата. Строки сообщений остаются с `deleted=false`, `attachment` хранит id файла. Поэтому сборщик мусора считает файл используемым, ключ файла в `keys.attachment_keys` живёт, объект в S3 остаётся, а `fileFor` продолжает его отдавать.

- **Чем грозит.** «Удалено навсегда» на файлы не распространяется.
- **Исправление.** При уничтожении истории помечать старые сообщения удалёнными или чистить их `attachment`; удалять ключи файлов, на которые больше никто не ссылается; ставить `attachment.purge`. В `fileFor` учитывать `history_from`.

### SSRF-1. Защита превью ссылок обходится IPv6-записью IPv4
`apps/server/src/domain/linkPreview.ts:57`

`isPublicIp` узнаёт адреса `::ffff:a.b.c.d` только в записи с точками. Парсер URL превращает `[::ffff:127.0.0.1]` в `[::ffff:7f00:1]`, и проверка считает адрес публичным. Не закрыты и `64:ff9b::/96`, `2002::/16`, `fec0::/10`. Дыра есть и для редиректов, и для `og:image`.

- **Чем грозит.** Любой вошедший пользователь заставляет сервер обращаться к внутренним сервисам.
- **Проверка.** Воспроизведено в контейнере.
- **Исправление.** Разбирать адрес в байты (`net.BlockList`), проверять вложенный IPv4, пропускать только глобальные адреса. Ограничить `/link-preview` по частоте.

### SSRF-2. DNS rebinding в превью ссылок
`apps/server/src/domain/linkPreview.ts:83`

Проверка адреса и само соединение резолвят имя отдельно.

- **Чем грозит.** Злоумышленник с коротким TTL отдаёт на проверку публичный адрес, а на соединение — внутренний.
- **Исправление.** Резолвить один раз и соединяться с проверенным IP, передавая `Host` и SNI исходного имени. Либо пускать превью через egress-прокси с политикой IP, в сети без маршрута к внутренним сервисам.

### INFRA-1. В production-конфигурации Postgres и Valkey открыты наружу
`docker-compose.secure.yml:24`

Overlay не переопределяет `postgres` (порт 5433, пароль `relay`) и `valkey` (порт 6380, без пароля). URL остаются нешифрованными. Чтобы стенд вообще запустился, приходится ставить обход `RELAY_PLAIN_INTERNAL=1`. SECURITY.md при этом обещает mTLS и `rediss`.

- **Исправление.** В overlay: `ports: !reset []` для postgres, valkey, s3 и kms; пароли из обязательных переменных; Postgres с `ssl=on` и `hostssl`; Valkey с паролем и TLS; внутренняя сеть.

### INFRA-2. Порт 8333 открывает весь API S3 с root-ключами из репозитория
`docker/seaweedfs/s3.json:5`

Единственная учётка S3 `relaydev/relaydevsecret` с правами Admin лежит в репозитории, и production её не меняет. nginx проксирует на 8333 весь API, а не только подписанные GET и PUT.

- **Чем грозит.** Знающий ключи — администратор бакета.
- **Исправление.** Учётки S3 из окружения; серверу — ключ без List и Admin. На 8333 пропускать только запросы с подписью (`X-Amz-Signature`) и только GET/HEAD/PUT отдельных объектов.
